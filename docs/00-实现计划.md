# sandboxd 最小实现计划

> Phase 1 已完成。当前 Phase 2 的详细技术规格以 docs/12-Agent层实现计划.md 为准；本文继续作为全项目模块总览。

## 目标

在 WSL2 中实现一个包含 gVisor 的 Kubernetes 沙箱 Demo。项目必须能运行、能演示、能解释，优先保持代码简单和中文注释清晰，不追求生产级完整性。

三条面试主线：

1. Pod 安全基线、gVisor、RBAC 和 NetworkPolicy 如何形成纵深防御；
2. informer、workqueue、预热池和 JSON Patch CAS 如何解决性能与并发问题；
3. server-side dry-run、双 Token 和代码白名单如何构成受控写路径。

## WSL 下的 gVisor 路线

先验证 Docker，再验证 Kubernetes：

```bash
docker run --rm --runtime=runsc alpine:3.20 dmesg | head
kubectl exec gvisor-smoke -- dmesg | head
```

两次输出都必须出现 `Starting gVisor`。

kind 通过 `extraMounts` 挂载：

- `runsc`；
- `containerd-shim-runsc-v1`；
- 新版 gVisor 的 `gvisor-bin/` 目录。

再通过 `containerdConfigPatches` 注册 `runsc` handler，并创建 `RuntimeClass/gvisor`。

## 模块范围

### PodSpec

- gVisor RuntimeClass；
- 非 root、drop ALL、seccomp、禁止提权；
- 只读根文件系统；
- 有 sizeLimit 的 `/tmp` 和 `/workspace`；
- CPU/内存限制和最长运行时间；
- 禁止自动挂载 ServiceAccount token；
- 手动 projected 短时 token、CA 和 namespace。

### Manager 和 Exec

- 创建 idle 或 busy Pod；
- 从 informer lister 等待 `PodReady=True`；
- 删除 Pod；
- remotecommand WebSocket 优先、SPDY fallback；
- exec 超时后使用独立 cleanup context 删除 Pod。

### 预热池

- 固定池容量和单 worker；
- handler 只向 workqueue 加固定 key；
- reconcile 统计 ready idle 和 provisioning idle；
- JSON Patch `test` 实现 CAS 认领；
- 池空时直接创建 busy Pod；
- Release 后删除，不复用。

### HTTP API

```text
POST   /api/v1/sandboxes
GET    /api/v1/sandboxes
DELETE /api/v1/sandboxes/{id}
POST   /api/v1/sandboxes/{id}/exec
POST   /api/v1/plans
GET    /api/v1/plans
POST   /api/v1/plans/{id}/approve
POST   /api/v1/plans/{id}/reject
GET    /healthz
GET    /readyz
GET    /metrics
```

公开 exec API 返回有限大小的 JSON stdout/stderr，不实现额外 WebSocket 协议。

### 审批门

只实现 Deployment scale：

- Agent Token 只能提交 Plan；
- Operator Token 才能批准或拒绝；
- 禁止系统 namespace；
- replicas 限制为 0–10；
- Propose 执行 server-side dry-run；
- Plan 保存 UID 和 resourceVersion；
- Approve 重新校验，防止审核后对象已改变。

### 指标

```text
sandbox_acquire_seconds{source="pool|direct"}
sandbox_pool_size{state="idle|busy"}
sandbox_claim_conflicts_total
sandbox_exec_seconds
sandbox_plan_denied_total{reason="namespace|replicas|target|changed|state"}
```

## 实现顺序

1. 安装工具，跑通 Docker gVisor；
2. 跑通 kind + gVisor RuntimeClass + Calico；
3. 建立 Go 工程、运行镜像和 PodSpec；
4. 实现 RBAC、NetworkPolicy、Manager、Exec 和基础 API；
5. 实现预热池、CAS 和指标；
6. 实现最小审批门；
7. 新增 Python agentd 和 LangGraph StateGraph；
8. 新增 Go 结构化 Kubernetes Diagnostic API；
9. 接入真实用户态 Prometheus/Alertmanager；
10. 完成 Live/Replay 告警诊断和 Prompt Injection 拒绝证据；
11. 完成 Agent 学习文档、面试问答、踩坑和 README。
12. Phase 2.1：补充 ToolResult 双通道、生命周期 Trace、上下文预算和取消清理闭环。

Phase 2 不进行 Agent 并发压测，只做单 Worker、单告警的最小真实链路。

Phase 2.1 不引入新 Agent 框架或通用 Coding Agent 能力，详细规格以 `docs/16-Pi-inspired-Agent内核优化计划.md` 为准。

每完成一个模块，同时编写对应学习文档和面试问答。

## 测试策略

只重点维护 Pod 安全基线测试。其他模块以 `go test ./...` 保证编译和少量纯逻辑，再用真实 kind 集群做 shell 验收，不追求覆盖率。

## 非目标

- 多租户、数据库、持久化审计；
- 多副本、leader election、动态池容量；
- CRD、Operator、通用写操作引擎；
- Web UI、TLS、公开 WebSocket 协议；
- Kata、Firecracker 和多集群；
- 生产级限流、恢复和测试体系。

## 完成定义

- kind Pod 确实运行在 gVisor；
- 只读 kubectl 成功，写操作被 RBAC 拒绝；
- NetworkPolicy 允许和拒绝路径都经过实测；
- 默认 5 并发认领无重复 ID，资源充足时最多验证 10 并发；
- dry-run、Agent 无批准权、Operator 批准执行形成闭环；
- `go build ./...`、`go test ./...`、`./hack/demo.sh` 可运行；
- README 没有未经实测的数字；
- 每个模块有对应学习文档和一分钟面试讲法。
