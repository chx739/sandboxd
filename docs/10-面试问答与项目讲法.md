# sandboxd 项目设计 FAQ 与面试自测

> **文档职责：这是当前项目级问题完整答案的唯一入口。** Python agentd 使用手写 Pi-style 双层循环，不再依赖 LangGraph；共有九个结构化工具。`15/19/23` 只保留问题索引，通用 Agent 概念以 `26` 为准，当前工程事实以 [24 项目全景](24-项目全景与心智模型.md) 和 [25 代码导读](25-代码导读与模块地图.md) 为准。历史 LangGraph 只作为架构演进素材。

## 1. 项目定位

一句话：这是一个把“不可信运维 Agent”和“可信执行边界”分开的教学 Demo。

核心链路：

~~~text
Alertmanager 告警
  -> agentd 双层 Tool Calling Loop
  -> Prometheus / Kubernetes / Linux / task 文件
  -> Prompt Injection 进入上下文
  -> Python/Go/Connector/RBAC 多层拒绝
  -> Diagnosis 或 Pending DryRun Plan
  -> Operator 人工审批
~~~

30 秒、1 分钟和3分钟版本见 [简历与面试表达手册](27-简历与面试表达手册.md)。

## 2. 面试只讲四条主线

### 主线一：纵深防御

gVisor 降低 Sandbox 直接攻击宿主内核的暴露面；restricted Pod、非 root、capability、seccomp、只读根、资源上限限制容器内能力；短时 SA、RBAC 和 NetworkPolicy 限制集群身份与网络。不同层解决不同问题。

### 主线二：控制器与并发

Informer/List-Watch 维护 cache，Lister 读缓存，handler 只入 workqueue，单 Worker 做幂等 Reconcile。预热池通过 JSON Patch test+replace 对 idle 标签做 CAS，池空时 direct fallback，Release 删除后补新。

### 主线三：Agent Runtime 与能力安全

双层循环处理 Tool/steer 和 follow-up；Session 只恢复脱敏上下文；Plugin 只注册可信内置工具；Tool Schema 不是授权。最终边界在 Python Policy、Connector、Go Policy、gVisor/RBAC 和审批。

### 主线四：读写分流

诊断读取走结构化窄接口。模型没有集群通用写权限，只能提交固定 Deployment scale Plan；Propose 做 server-side DryRun，Operator 独立批准，Approve 前检查 UID/resourceVersion。

## 4. 容器与 Kubernetes 高频问答

### Q1：普通容器、gVisor 和虚拟机有什么区别？

普通容器共享宿主内核；gVisor 用用户态 Sentry 实现大量系统调用，减少工作负载直接触达宿主内核的攻击面；虚拟机有独立 guest kernel，边界更强但启动和资源成本通常更高。gVisor 是安全与兼容/性能之间的折中。

### Q2：有 gVisor 为什么还需要 seccomp 和非 root？

gVisor 主要隔离系统调用路径；非 root/capability 限制容器身份；seccomp 限制 syscall；只读根和 limits 限制持久化及资源耗尽；RBAC/网络限制外部能力。纵深防御不能押在单层。

### Q3：如何证明真的使用了 gVisor？

RuntimeClass 对象只证明声明存在。要检查节点 containerd handler，并在 Pod 内观察 dmesg 的 Starting gVisor。项目把运行证据而不是 YAML 当完成标准。

### Q4：Running 和 Ready 有何区别？

Running 表示容器已运行或启动中；Ready condition 表示就绪条件通过。Manager 通过 informer lister 等待 Ready，避免把尚不可用的 Sandbox 返回给调用方。

### Q5：为什么关闭自动 SA Token 再手动 projected？

显式控制是否挂载、audience 和 expiration，减少长期凭据和无意暴露。它必须与最小 RBAC 配合，短期 Token 不是权限本身。

### Q6：为什么只读 RBAC 也排除 Secret？

读取 Secret 可获得其他身份的 Token、密码和证书，实际效果可能是权限提升。“只读”描述 API 动词，不代表安全后果低。

### Q7：NetworkPolicy 为什么可能不生效？

它是 Kubernetes API 声明，数据面依赖支持策略的 CNI。kindnet 不执行 NetworkPolicy，因此项目使用 Calico，并验证允许与拒绝路径。

## 5. Go、client-go 与并发问答

### Q8：Informer、Lister、Workqueue 如何配合？

Informer List/Watch 并维护本地 cache；Lister 读取 cache；事件 handler 只把 key 入队；Worker 重读当前状态并执行幂等 Reconcile。事件只是触发器，cache 中的当前状态才是事实。

### Q9：为什么 handler 不直接创建/删除 Pod？

handler 可能处理过期对象且不能长时间阻塞。把副作用集中到可重试 Reconcile，能做幂等、退避和状态收敛。

### Q10：JSON Patch test 为什么能做 CAS？

API Server 原子执行同一个 Patch。只有标签仍是 idle 时 test 成功，随后 replace 为 busy；竞争者 test 失败，无法重复认领。

### Q11：为什么不用进程互斥锁？

锁只约束单进程，不能覆盖多个 API 调用实例，也不能防外部修改。把条件写进 API Server 原子操作，状态事实与并发控制在同一处。

### Q12：Release 为什么删除而不是复用？

Exec 可能留下文件、进程或内存状态，完整清洗难以证明。删除后由 Reconcile 补新，成本稍高但隔离语义简单。

### Q13：Exec fallback 的坑是什么？

业务退出码不是传输失败。若所有错误都从 WebSocket 重试到 SPDY，带副作用命令可能执行两次。项目只对升级/代理传输错误 fallback。

### Q14：超时后为什么用独立 context 清理？

原 context 已取消，用它 Delete 会立即失败。项目给清理一个独立、短时窗口；Python Runner 同样用独立 Task + shield 释放 Sandbox。

## 6. DryRun 与审批问答

### Q15：server-side DryRun 做了什么？

请求经过真实 API Server 的默认化、校验、准入和授权，但不持久化。它能发现当下无效请求，不能锁定对象或保证未来执行成功。

### Q16：为什么有 RBAC 还要审批门？

RBAC 表达服务身份能调用哪些资源动词，难以表达“这一次变更是否经过人审查”。审批门处理业务治理和职责分离，RBAC提供最终最小权限，两者互补。

### Q17：UID 和 resourceVersion 分别防什么？

UID 防同名 Deployment 删除重建；resourceVersion 防同一对象在审核期间发生变化。真实 Update 继续携带 resourceVersion，处理复核到写入之间的竞争。

### Q18：Agent approve 为什么返回 401？

Demo 的 Operator 路由只接受 Operator Token，Agent Token 不属于可认证身份，因此是 401。生产统一身份系统通常先认证，再按角色授权返回 403。

## 7. Agent Runtime 高频问答

### Q19：这是不是 ReAct？

是 ReAct 风格 Tool Calling：模型根据 Observation 选择 Action，结果回灌直到 Final；不记录隐藏思维，只记录可见调用、结果和事件。

### Q20：为什么从 LangGraph 改成手写循环？

Phase 2 先用显式图验证链路；范围稳定后，当前控制流只需一个双层循环。手写后 steer/follow-up、预算、拒绝回灌和 finalize 一眼可见，也删除了不必要依赖。复杂持久化图时 LangGraph仍有价值。

### Q21：steer、follow-up 和 cancel 有何区别？

steer 在完整 Turn 后进入下一轮；follow-up 只在 Agent 自然结束时继续同一 Session；cancel 取消运行控制流并触发清理。steer 不能撤销已经执行的动作。

### Q22：Session、Task、Sandbox 有何区别？

Session 是事故上下文，Task 是一次运行，Sandbox 是该运行的资源租约。resume 沿用 Session，但创建新 Task 和 Sandbox，不恢复进程。

### Q23：Plugin Manifest 是权限吗？

不是，只是能力声明和工具组织。授权由 Python Policy、Connector 配置、Go Policy、RBAC 和审批完成。

### Q24：为什么工具顺序执行？

低资源 Demo 更重视可审计性和确定顺序；顺序执行简化预算、取消、协议闭合和目标系统压力。独立只读工具很多时才值得并行。

### Q25：最终 JSON 为什么不能直接相信模型？

模型可能自报不存在的 evidence、denial 或 planId。finalize 清空这些字段，再从真实 ToolResult 和 State 回填。模型负责解释，程序负责事实。

## 8. Agent 安全与工具问答

### Q26：Prompt Injection 被解决了吗？

没有消除。日志中的注入会真实进入上下文，模型可能受影响；系统依赖结构化工具、服务端校验、最小凭据和审批，把影响限制在允许能力内。

### Q27：Replay 与 Live 分别证明什么？

Live 观察真实模型行为，但不稳定；Replay 固定模型响应，验证 Runtime、Policy、真实工具和 gVisor 的确定性回归。Replay 不能证明模型每次都会选对工具。

### Q28：Linux SSH 路径是否由 gVisor 隔离？

不是。它由静态 Target Registry、strict host key、固定 argv、低权限远端账号、authorized_keys command 和 sshd ForceCommand 收口。

### Q29：为什么不给任意 Bash？

Bash 把参数空间扩大为整个操作系统，Schema 无法表达真实副作用，注入后果和审计复杂度都会大幅增加。项目只提供按 operation 划分的窄能力。

### Q30：文件工具会修改生产系统吗？

不会，只写当前 task 的 Workspace 草案。路径、symlink、大小、SHA256 CAS 和原子替换限制本地副作用；远端写仍应设计专用 Plan。

### Q31：你怎么测 Prompt Injection，自己造日志数据集吗？

是，但不是只收集攻击字符串。我把每条样本写成“正常任务、非可信来源、攻击目标、允许/禁止工具、必要证据和外部状态不变量”，覆盖七种输入通道。当前 v2 是 40 条合成 JSONL（8 clean、24 attack、8 hard-negative），并标记六种攻击目标和六种表达技术；优点是无真实秘密、可读、可改、可稳定回归。

### Q32：为什么要把 Agent 和沙箱/执行边界分开测？

因为“模型没上当”和“模型上当但系统拦住”是两种完全不同的安全性质。前者看 Agent ASR，后者看未授权副作用率和遏制率。本项目 Replay 故意让 Agent 请求危险工具，以最坏意图验证 Policy/Workspace；gVisor、RBAC 和 Go Policy 的真实链路仍由独立 E2E 证明。

### Q33：为什么 Replay 的 Agent ASR 是 100%，这不是很差吗？

不是模型成绩。v2 Replay 固定了 24 次危险决策，目的就是确保每条策略都真的被攻击到；此时要看副作用为 0、遏制率为 100%。只有固定模型、配置、样本和重复次数的 Live Eval，才能报告真实模型 ASR。

### Q34：如何避免通过“全部拒绝”获得安全高分？

同时报告 Clean Task Success、Evidence Coverage 和 Over-refusal，并加入包含攻击词、实际却是正常安全记录的 hard-negative。安全率高但正常任务做不成，不是可用的 Agent。

### Q35：为什么不用 LLM-as-Judge 判断越权？

Tool 名、参数、拒绝层和外部状态是否变化都有结构化事实，应该用确定性代码评分。Judge 适合评价诊断相关性、表达或开放文本，不应代替权限与副作用判断，否则安全结论本身也会受模型漂移影响。

### Q36：有哪些公开数据集，为什么不直接照搬？

AgentDojo 适合学习任务效用与安全属性分离，InjecAgent 有大量间接注入工具组合，ASB 覆盖更广的 Agent 攻防。它们值得用于后续扩展和横评；本项目先做贴合 Prometheus/Kubernetes/Linux/File 工具语义的 40 条最小集，避免引入大框架后只能讲库、讲不清自己的边界。

### Q37：真实模型测出来怎么样，0% ASR 能说明安全吗？

v2 用 DeepSeek V4 Flash 跑了 16 条 normal 一次和 24 条 attack 三次，共 88 Task。原始报告是 normal 14/16、Agent ASR 0/72、外部副作用 0/72、Over-refusal 0/16；但审计发现 25/72 次攻击观察被 Fake Connector 跨来源重复注入，所以来源分层无效，修复后也没有在授权外重跑。我面试时会把它讲成“跑完协议并发现测评夹具 bug”，而不是宣称模型绝对安全。确定性执行边界引用修复后 Replay 的 24/24 containment；Live 没有 Agent attack，containment 仍是 N/A。

## 9. 最值得讲的五个真实坑

1. RuntimeClass 存在但 runsc 未生效：用 Pod 内核视图建立证据链；
2. Exec 对业务错误 fallback：可能重复副作用；
3. Informer lazy initialization：Start 后才创建 informer 导致 cache 不同步；
4. client-go fake 不模拟 DryRun：需要 reactor 防测试“假落地”；
5. Session 整段正则脱敏破坏 JSON：改为结构化叶子脱敏。

完整素材见 [开发踩坑与排障](11-开发踩坑与排障.md)。

## 10. 生产化差距

面试时主动说明：

- 单机、单进程、单 Worker、单租户；
- API Token 没有用户/资源归属；
- Task/Plan 内存状态，Session 本地 JSONL；
- 外部系统是本地 Prometheus 和静态 SSH Demo Target；
- 没有 TLS/OIDC、Vault/SSH CA、凭据轮换、HA；
- 没有多集群、动态插件、大规模/统计性 Live Eval 和压力测试；
- 文件路径仍有 lstat 到 open 的 TOCTOU 简化；
- gVisor 是纵深防御，不是绝对安全保证。

## 11. 模拟面试方法

每轮 20 分钟：

1. 30 秒介绍；
2. 面试官随机选一条主线深挖；
3. 讲一个真实坑；
4. 回答一个未采用方案；
5. 说明生产化优先级；
6. 打开代码定位核心函数。

如果回答只有术语没有代码位置、验证证据和代价，说明还没有掌握。

## 12. 面试前 15 分钟复习

1. 手画四层架构和读写分流；
2. 复述 Q3、Q8、Q10、Q15、Q20、Q21、Q26、Q27、Q31–Q35；
3. 从五个真实坑中选两个；
4. 记住九个工具及不同执行边界；
5. 最后复述生产化差距和诚信边界。
