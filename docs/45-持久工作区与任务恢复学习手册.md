# 持久工作区与任务恢复学习手册

> Phase 9 实现中。规格见 [43](43-工作区持久化与恢复实施约束-NFS-v1与restic-MinIO-v2.md)，目标 Prompt 见 [44](44-工作区恢复目标模式Prompt.md)。本文区分已写模块与尚未接线的完整流程；不能用单测代替真实恢复验收。

## 1. 先分清四份数据

| 数据 | 回答的问题 | 权威位置 |
|---|---|---|
| Session 节点树 | Agent 已经说过什么、看到什么？ | 沙箱外 JSONL |
| Task 恢复账本 | 哪个任务还应运行、用过多少额度、谁在执行？ | 沙箱外私有 Linux 控制目录 |
| Workspace | 最新的报告和配置草案是什么？ | Pod 的专属 NFS 目录 |
| V2 检查点 | 哪个完整会话节点对应哪个历史文件树？ | 检查点元数据 + restic/MinIO |

Pod 是可替换执行资源。NFS 保住文件，任务账本和 Session 才能说明如何接着运行；只有挂载成功还不等于任务恢复。

## 2. 当前已实现的基础模块

### 2.1 DurableJournal

代码：`agentd/app/runtime/durable.py`。

- 持有独占 flock，防止同一日志出现两个活动写入者。
- 规范 JSON、连续 seq、SHA256 检测意外损坏；checksum 不是防恶意管理员篡改的签名。
- 每次追加后 fsync，成功后才更新内存视图。
- 启动只忽略缺少换行的断尾；完整坏行拒绝启动。
- 写盘失败后停止该实例继续追加，重新启动时再检查持久内容。
- 控制文件必须具备真实 Linux 私有权限，拒绝 Windows 挂载盘假 chmod；测试在原生 `/tmp` 夹具运行，部署目录须为持久 Linux 目录。

### 2.2 RecoveryLedger

代码：`agentd/app/runtime/recovery.py`、`runtime/execution.py`、`store.py`、`runner.py`；部署入口已接入持久TaskStore与远程Runner，真实故障验收仍逐项进行。

每次状态变化保存有界完整投影，使恢复过程容易读懂，不引入数据库。Task 的 session、branch、workspace 和调用预算限额一旦登记便不重置。

新任务使用 schemaVersion=2 分阶段时钟：排队尚未开始不计 claim 时间；第一次 attempt 开始时持久化 claimStartedAt 与190秒截止时间。首次绑定成功后，用 begin_loop 开启独立120秒循环窗口。以后自动接续只能沿用这两个时间锚点，重新认领也计入当前阶段剩余时间。首次 claim→loop 是原预算语义中的阶段转换，不是恢复补发额度。时钟早于已保存 attempt 开始时间时停止，避免回拨增加额度。

旧 schemaVersion=1 的显式 deadline 仍按原值读取和执行，不改写历史、不推算缺失时间、不补发循环窗口。清理仍须由 Runner 使用独立有界窗口，并可在任务过期后执行；这部分 Runner 接线尚未完成。records() 保留取消/过期但资源未处理完的记录，启动清理不能只扫描可继续调用模型的 candidates()。

例子：t=0 开始首次认领，t=180 认领成功，循环截止为 t=300。t=220 进程退出、t=260 重启，则接续认领和后续循环总共只剩40秒；如果认领又花20秒，模型与工具仅剩20秒。若首次认领未成功就在 t=180 中断，接续只能用原认领窗口剩下10秒。清理不发起新的模型调用，用独立窗口结束资源归属。

```text
queued → running / attempt-1
                   ↓ 旧执行者已确认停止
             interrupted
                   ↓ 同 task_id，原 deadline/额度
             running / attempt-2

cancel → cancelling → 资源处理完成 → cancelled
```

- 发起调用前 reserve，记录 model/tool/router 次数；结果未知的 reserved 转为 uncertain，仍占预算。
- 文件正文不复制进账本，只保留操作、路径、目标 hash；不在恢复模块里直接重放写入。
- 模型选择登记一次，自动接续不能重新路由到另一模型。
- steer/follow-up 保存 command_id 和 appliedNodeId；后续 Session 接线必须同时记录命令 ID，处理跨日志提交中断。
- owner_stopped 是受信任 Runtime 的事实登记入口，**它本身不检查 Kubernetes**。只有后续 Go 对账真正确认旧执行者终止后才能调用；删除 Pod 对象或租约过期都不算证明。
- 终态不复活；取消优先；默认最多两次自动恢复。

### 2.3 Pod 内文件 helper

代码：`cmd/sandbox-filetool` 和 `internal/workspace`。生产入口固定 `/workspace`，文件调用只接一个有界 JSON 请求，没有自由 Shell/argv/root 参数。可信启动路径另有固定 `--check`，通过私有临时文件的写入/fsync/删除确认存储，不作为模型工具。

保留 list/read/search/write/edit、256 KiB 单文件、8 层/512 bytes 路径、CAS、原子替换、脱敏和有界 diff。新 Go 实现的 diff 是简单单 hunk，不保证最小差异，与 Python 的 difflib 排版可以不同。

JSON层区别必填参数缺失、null与合法空字符串，拒绝无效UTF-8；Go内部序列化也保留显式空内容，避免空文件写入被误判。写入/fsync/rename等存储错误采用单独执行错误通道（helper退出3→HTTP503），不把结果不明写入伪装成CAS/路径策略拒绝。

目录逐层通过目录文件描述符与 `openat(O_NOFOLLOW)` 打开；普通文件还拒绝 FIFO、设备、symlink 与多硬链接。写入临时文件后先 fsync，再 rename、fsync 父目录。写盘确认失败须视为结果不明，不能自动当作“没有写”。

工具级互斥锁防止两个 helper 同时通过同一旧 hash；它补充 Go 的归属检查，不能代替跨 Pod fencing。

NFS 的 PV capacity 不提供真实磁盘配额。helper 采用 64 MiB、512 项的有界扫描限制；这是应用配额，不是任意 Pod 进程的服务器磁盘硬配额。中断遗留的私有临时文件计入配额并保留，不列为用户文件；清理由后续显式维护处理。

### 2.4 专属 Pod / PV / PVC 构造

代码：`internal/sandbox/workspace_spec.go`。

- 从原 BuildPod 复用 gVisor、非 root、只读根文件系统、drop ALL 等约束。
- 专属 Pod 创建时确定 PVC，直接 busy，不从无状态预热池修改挂载。
- NFS server 由可信配置给出明确 IP，路径固定 `/workspaces/<workspace_id>`，不接受模型自选 endpoint 或目录。
- 固定 NFSv4.1/TCP、hard 挂载、Retain 回收策略；RWO 本身不构成 NFS 单写入保证。
- hard 挂载保护写入语义，但服务失联时内核 I/O 可能阻塞；不能把 RPC 超时当旧写入者已经死亡。

### 2.5 Go 持久绑定与旧路径隔离

代码：`internal/control`、`internal/sandbox/workspace_registry.go`、`internal/workspace/init_linux.go`。

Go 独立持有自己的 JSONL，不与 Python 共写。工作区状态为：

```text
registered → ready → starting → bound → stopping → released
                         ↓                   ↑
                   创建请求结果不明：保留状态，阻止新 owner
```

工作区归属固定在 session/branch；每次 owner 变更增加 generation。记录 CreateSubmitted 是为了区分“尚未发送创建请求”和“请求已经发出但不知道结果”，后者不能凭没找到 Pod 就当作从未创建。

文件请求须匹配 workspace/task/attempt/sandbox/generation。`WithOwner` 将文件访问与归属切换串行化，当前采用全局锁适配单 Worker，不宣传并发性能。自动接续还检查原镜像身份，不能因 tag 变化静默切镜像。

`ConfirmStopped` 只由 Go 的可信 Kubernetes 对账调用。新增 `WorkspaceRuntime` 已连接真实采集：固定 `RestartPolicy=Never`、全部容器终止、NodeReady 与近期 Node Lease，再记录停止证明和移除专属 finalizer。finalizer 只保留对象和证据，本身不会杀进程；对象NotFound、租约过期或递增generation都不能代替终止证明。

可信目录初始化入口固定 `/workspace-root`，只接格式固定的 workspace_id；现有目录权限或身份不匹配时拒绝，不递归修改旧文件。已接入独立sandboxd-storage命名空间的短生命周期维护Pod：仍用gVisor/非root/只读根，禁API凭据与Pod网络；仅该可信路径挂父目录，业务Pod只挂专属目录。

已关闭持久工作区的旧通用 `/exec` 和无归属释放路径；预热池忽略工作区 Pod，不认领或清理它，防止抢走工作区或删掉终止证据。旧无状态演示路径保留。

### 2.6 HTTP 与 Python 远程文件适配器

Go 已接以下 Agent Token 接口；Operator Token 不代替 Agent 身份：

| 接口 | 用途 |
|---|---|
| POST /api/v1/workspaces | 登记作用域、可信初始化目录/PV/PVC |
| GET /api/v1/workspaces/{id} | 读取持久绑定/执行状态 |
| POST .../{id}/claim | 创建专属Pod并验证读写后绑定 |
| POST .../{id}/release | 校验旧归属与UID，收集终止证明后释放 |
| POST .../{id}/files | binding + 固定request；Go与执行侧独立校验 |

启动时同时配置 `--workspace-nfs-server`、`--workspace-image`、`--workspace-control-dir`；控制目录必须为原生Linux持久路径，不能放/tmp等临时目录。不配置时保留旧无状态服务模式，工作区接口明确503。

`agentd/app/tools/remote_files.py` 提供不创建本地目录的适配器；FileToolsPlugin已可接收它。工作区绑定由Runner给出，模型不能用参数换workspace/attempt。确认丢失时不自动重试：区分执行故障、归属错误和正常策略拒绝；Loop收到执行故障立即退出本attempt，不能继续问模型重发原写入。

部署入口 `load_settings` 默认选择 `nfs`，TaskStore向Runner传RecoveryAttempt，文件工具实际选择RemoteFileWorkspace。`AGENTD_RECOVERY_DIR`默认`~/.local/share/sandboxd/agent-control`，拒绝相对路径和/tmp等临时目录；DurableJournal还检查真实Linux私有权限。Go须配置前述三个工作区参数。

`AGENTD_WORKSPACE_BACKEND=local`仅用于旧离线演示；直接构造Runner而不传恢复上下文仍是旧夹具路径。手工构造Settings的旧测试保留local默认，部署环境读取函数默认nfs。旧task业务文件不删除、不默认双写；旧Session查询可回退到原trace目录。旧无工作区映射的会话拒绝携带工作区恢复，显式文件迁移入口仍待完成。

### 2.7 Session 多 attempt 视图

`SessionJournal.for_attempt(attempt_id)` 共用原文件和进程内锁，为新事件增加 attemptId。增量快照、消息前缀、run 起点和安全 head 按 taskId + attemptId 定位；旧记录缺字段时仍按 legacy 读取，原始字节不改写。

新 attempt 从当前已持久化的完整 head 接续。上一 attempt 的半组工具调用保留审计，但不进入新上下文；新的消息接在完整父链上，避免重复复制旧节点。旧 attempt 不能追加或重新激活；相同起点初始化和相同 transcript 重试幂等。append_transcript 返回 fsync 后的安全 nodeId，供后续任务账本登记完整边界。

TaskStore/Runner现已选择该视图。V1携带工作区从旧节点恢复会返回409，树和父链仍可读；最新节点手动resume新建Task并沿用稳定branch/workspace。强杀进程、故障及预算的正式验收以独立真实报告为准，不能用模块测试替代。

### 2.8 自动接续流程与结果不明

```text
服务启动 → 从tasks.jsonl重建Task及待执行列表
        → 先对账旧attempt，不把服务退出记为用户取消
        → Go确认旧执行者停止；未确认则interrupted并阻止接管
        → 检查取消/终态/原阶段截止时间/剩余额度/恢复次数
        → 同task_id新增attempt，重新绑定原workspace
        → 加载完整Session父链、恢复Provider配置与Replay游标
        → 继续同一手写Loop
```

- `RecoveryAttempt`在模型/允许执行的工具调用前预留额度，成功响应后确认；结果不明仍占预算。恢复时模型轮数、工具次数及Prometheus次数从账本重建。
- Provider保存不含Key的配置指纹，Replay还绑定固定响应文件hash。自动恢复不重新选模；路由请求已有预留但结果未保存时，只用部署者配置的固定强模型回退。持久Live调用要求Provider自动重试为0。
- 认领前先持久化claimRequested。没收到响应时查Go归属，不能只凭Python没有ID、Go返回ready/404就声明从未创建。能确认本进程尚未发起认领，才可登记never-bound。
- 旧write_file结果不明时，新attempt只读核查当前hash；匹配预期内容才继续，不重发原写入。edit缺少可证明的新hash或内容不匹配时核查后安全停止；不明Plan提交也停止，不自动重新提交。
- 接收的steer/follow-up先保存命令ID。完整会话节点仅保留允许的commandId元数据；完整边界落盘后更新消费游标。跨日志崩溃窗口从已保存Human节点补认游标，已有ID不再注入。
- 每个attempt的Trace以独立`attempt.trace`事件保存在任务账本，不被最终Trace覆盖。GET `/api/v1/tasks/{id}/traces`受Agent Token保护，返回全部尝试；原`/trace`保留最新视图。进程强杀导致无Trace时，只补控制面中断事实并标记usageKnown=false，不虚构模型用量。
- 默认最多2次自动恢复，即最多3个attempt。取消先落盘再打断；终态任务不重新调模型。任务状态interrupted表示仍有资源或执行状态待核查，不冒称已经失败清理完成。
