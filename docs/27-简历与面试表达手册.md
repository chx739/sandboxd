## 1. 项目名称建议

**sandboxd：基于 gVisor 的安全运维 Agent 沙箱**

## 2. 简历一句话

基于 Go、Kubernetes client-go、gVisor 和 Python 实现安全运维 Agent Demo，打通 Alertmanager 告警、Prometheus/Kubernetes/Linux 诊断、Pi-style Tool Calling、Prompt Injection 隔离和 DryRun 人工审批闭环。

## 3. 简历三条推荐版本

- 在 WSL2 单节点 kind 中集成真实 gVisor runsc，构建 restricted Pod、短时 projected ServiceAccount Token、最小只读 RBAC 与 Calico default-deny NetworkPolicy，并通过 Pod 内 dmesg、RBAC/网络正反路径验证隔离生效。
- 基于 client-go Informer/Lister、typed Workqueue 实现大小为 2 的预热池，以 JSON Patch test+replace 完成并发 CAS 认领；实测 5 个并发请求获得 5 个唯一 Sandbox，并保留 pool/direct 和冲突指标。
- 使用 Python 手写 Pi-style 双层 Agent Loop，接入 Prometheus、gVisor Kubernetes 诊断、受限 SSH 和 task 文件工具；通过 Python/Go Policy、RBAC 与 Agent/Operator 双 Token 审批限制间接 Prompt Injection 和危险写操作。

如果版面只能放两条，保留第一条和第三条；第二条作为后端/Go 岗定制。

## 5. 30 秒介绍

“我做了一个安全运维 Agent Demo。外部 Alertmanager 告警进入 Python Agent，Agent 通过手写的 Pi-style Tool Calling 循环查询 Prometheus、Kubernetes 和受限 Linux Target。Kubernetes 诊断真实运行在 gVisor 沙箱中，沙箱还有 restricted Pod、最小 RBAC 和 default-deny 网络。模型不能直接写集群，最多提交经过 server-side DryRun 的 Deployment scale Plan，再由独立 Operator Token 审批。我还用 Pod Log 和 Linux Log 做了间接 Prompt Injection，证明安全依赖执行层边界而不是 Prompt。”

## 6. 一分钟介绍

“这个项目解决的是运维 Agent 的权限问题，而不是单纯让模型会调用工具。外部告警先进入 agentd，模型在有限轮数内选择九个结构化工具。Runtime 是我参考 Pi 思路手写的双层循环，支持 steer、follow-up、cancel、线性 Session 和受信任内置插件。

可信执行层由 Go sandboxd 负责。它用 client-go 管理真实 gVisor Pod，Pod 使用非 root、只读根文件系统、短时 SA、只读 RBAC 和 NetworkPolicy。为了降低冷启动，我用 Informer/Workqueue 维护预热池，通过 JSON Patch test+replace 做 CAS 认领。对于写操作，Agent 只能创建 Deployment scale Plan，先 server-side DryRun，再由 Operator Token 审批，并通过 UID/resourceVersion 防审批期间对象变化。

我做了 Replay 和 DeepSeek Live 两类实验。Live 反映模型行为，Replay 负责确定性触发危险动作，最终分别被 Python Policy、Go Policy、RBAC 和审批门拦截。”

## 7. 三分钟展开结构

不要按 Phase 1、2、3、4 报流水账。按问题讲：

### 第一部分：为什么做

“运维 Agent 会读取日志、告警和配置，这些内容可能带间接 Prompt Injection；同时运维凭据副作用很大，所以不能让模型直接拥有通用 Shell 或 kubeconfig。”

### 第二部分：怎么做

讲四条链：

1. Agent：Alert -> Task -> 双层 Loop -> Tool -> Diagnosis；
2. Kubernetes：Tool -> Go 固定 operation -> gVisor Pod -> 短时 SA -> RBAC；
3. 外部主机：targetId + operation -> 固定 SSH argv -> strict host key -> forced-command；
4. 写操作：propose -> DryRun -> pending -> Operator approve -> TOCTOU 复核。

### 第三部分：最有技术含量的机制

选择两个深入：

- Informer/Workqueue + JSON Patch CAS；
- Prompt Injection 的纵深边界；
- Context/ToolResult/Session 的 Agent Runtime；
- DryRun + 双 Token + UID/resourceVersion。

### 第四部分：证据和边界

“我用 Pod 内 Starting gVisor、RBAC/NetworkPolicy 正反路径、5 并发唯一认领、Agent approve 401、stale Plan 409、Replay contained 和 Live not-triggered 作为证据。它仍是单机单租户 Demo，没有 HA、数据库和生产凭据系统。”

## 8. 三个 STAR 深挖素材

### 素材一：Exec fallback 可能重复执行

**Situation**：client-go Exec 优先 WebSocket，最初考虑失败后统一回退 SPDY。

**Task**：既兼容代理环境，又不能重复执行有副作用的命令。

**Action**：区分传输升级错误与远端业务退出码，只对前者 fallback；stdout/stderr 限长；超时后用独立 context 删除 Pod。

**Result**：实测 exitCode=7 不重放，超时返回 504 且 Pod 被清理。

**面试价值**：错误分类、幂等性、context 取消和补偿动作。

### 素材二：RuntimeClass 存在不代表 gVisor 生效

**Situation**：Kubernetes 对象创建成功，但这只证明声明存在。

**Task**：给出运行时真的由 runsc 承载的证据。

**Action**：逐层检查 RuntimeClass handler、kind 节点 containerd 配置和 Pod 内核视图，最终用 Pod 内 dmesg。

**Result**：得到 Starting gVisor 真实输出，并写入自动验证。

**面试价值**：声明面与数据面、证据链和不冒充成功。

### 素材三：Session 脱敏不能先破坏 JSON

**Situation**：最初对整段 Tool 参数 JSON 做正则脱敏，可能替换引号或截断，导致 JSONL 无法恢复。

**Task**：既不保存凭据，又保持结构化 Session 可解析。

**Action**：改为对对象叶子递归脱敏，再序列化；同时不保存模型 additional_kwargs 和隐藏思维。

**Result**：Session resume 测试稳定，Bearer 告警注解也被回归覆盖。

**面试价值**：结构化数据处理、隐私和可恢复性。

## 9. 高频追问的答题框架

统一用四步：

~~~text
先给结论
  -> 解释机制
  -> 引用本项目证据
  -> 主动说代价/生产边界
~~~

示例：“为什么不用任意 Bash？”

“因为 Bash 会把模型能力扩大到整个操作系统，Schema 很难表达真实权限。本项目把 Kubernetes、Linux 和文件分别做成结构化窄工具，且后端重复校验。代价是灵活性下降；生产中若确实需要命令执行，我会按目标和操作生成审批 Plan，而不是直接开放 Shell。”

## 10. 面试官最可能深挖的十二题

1. gVisor 与普通容器、虚拟机、Kata 有何区别？
2. 为什么有 gVisor 还需要非 root、seccomp、RBAC 和 NetworkPolicy？
3. Informer、Lister、Workqueue 怎样配合？
4. JSON Patch test 为什么是 CAS？
5. server-side DryRun 能保证审批后成功吗？
6. Tool Schema 为什么不是安全边界？
7. 为什么从 LangGraph 改成手写 Loop？
8. steer、follow-up、cancel 有何区别？
9. Prompt Injection 如何进入上下文，为什么没有被真正“消除”？
10. Replay 和 Live 分别证明什么？
11. SSH 为什么不经过 gVisor，如何保证安全？
12. 项目离生产还缺什么？

准备时每题控制在 45–90 秒。

## 11. 怎样讲开发演进

如果面试官问“你怎么迭代的”，再讲 Phase：

~~~text
Phase 1：先做真实 Kubernetes/gVisor 可信底座
Phase 2：用 LangGraph 打通外部告警和 Tool Calling
Phase 2.1：抽离 ToolResult、事件、Context 和取消清理
Phase 3：范围稳定后手写 Pi-style Loop，加入 Session/Plugin/控制
Phase 4：接入受限 Linux Target 和安全文件工作区
~~~

强调每次演进解决了什么问题，不要只说增加了什么文件。

## 13. 如何回答“代码是不是 AI 写的”

“项目开发中使用了 AI 辅助，但架构范围、安全边界和验收证据是我按模块控制的。我没有把生成代码当完成标准，而是通过正反实验验证 gVisor、RBAC、NetworkPolicy、CAS、审批和注入边界。为了真正掌握，我按调用链阅读代码、做破坏实验，并把 47 个真实问题整理成排障文档。”
