# 代码导读与模块地图

> 这不是文件清单，而是一条从请求入口走到资源边界的阅读路线。每读完一段，先合上文档复述调用链。

## 1. 仓库分成六块

~~~text
cmd/ + internal/       Go 可信执行层
agentd/app/            Python Agent Runtime
deploy/                Kubernetes、可观测性和 SSH Target 配置
hack/                  可复现实验与低资源 E2E
docs/evidence/         脱敏证据
docs/                  学习、面试和历史计划
~~~

代码阅读时不要从工具函数逐个点开。先沿主链走一遍，再学习横切安全机制。

## 2. 第一条主链：sandboxd 怎样启动

阅读顺序：

1. cmd/sandboxd/main.go
2. internal/config/config.go
3. internal/api/server.go
4. internal/sandbox/manager.go
5. internal/sandbox/pool.go
6. internal/approval/service.go

在 main.go 中找到下面几个组装动作：

- 创建 Kubernetes ClientSet；
- 先取得 Pod informer，再启动 SharedInformerFactory；
- 创建 Manager、Pool、Approval Service；
- 启动 Pool worker；
- 创建 HTTP Server；
- 进程退出时通过 context 停止控制循环。

这里要回答：

- 为什么 informer 必须在 factory Start 之前实例化？
- 为什么 Manager、Pool、Approval 分成三个对象？
- 为什么 Pool 是后台控制器，而 Manager 是同步生命周期接口？

## 3. 第二条主链：申请一个 Sandbox

入口：

~~~text
POST /api/v1/sandboxes
  -> api.Server
  -> Pool.Claim
  -> JSON Patch CAS
  -> 没有 idle 时 Manager.Create
~~~

重点阅读 internal/sandbox/pool.go：

### Pool.Reconcile

它从 informer cache 统计 ready idle 和 provisioning idle，让总数逼近 target。事件 handler 只负责放一个固定 key，真正副作用都在 Reconcile。

### Pool.Claim

它对候选 Pod 发送 JSON Patch：

~~~json
[
  {"op":"test","path":"/metadata/labels/sandbox.io~1state","value":"idle"},
  {"op":"replace","path":"/metadata/labels/sandbox.io~1state","value":"busy"}
]
~~~

test 和 replace 在 API Server 原子执行，因此多个 HTTP 请求不会同时认领同一个 Pod。

### Pool.Release

Release 删除 Pod，不做清洗复用。这样牺牲少量启动成本，换来更简单的隔离语义。

读完后能回答：

- 为什么只用进程锁不够？
- 为什么 provisioning 也计入池容量？
- CAS 冲突为什么不是错误指标？
- pool miss 为什么允许 direct fallback？

## 4. 第三条主链：Pod 安全基线怎样落地

阅读 internal/sandbox/spec.go，对照：

- deploy/namespace.yaml
- deploy/rbac.yaml
- deploy/networkpolicy.yaml.tmpl
- deploy/runtimeclass.yaml

BuildPod 里重点看：

- runtimeClassName 选择 gVisor；
- runAsNonRoot 和固定 UID/GID；
- allowPrivilegeEscalation=false；
- capabilities drop ALL；
- RuntimeDefault seccomp；
- readOnlyRootFilesystem；
- CPU/内存、emptyDir sizeLimit、ActiveDeadline；
- automountServiceAccountToken=false；
- 手动 projected Token、CA、namespace。

四份配置分别负责：

| 位置 | 作用 |
|---|---|
| PodSpec | 每个工作负载主动声明安全基线 |
| PSA restricted | 代码漏字段时由准入层兜底 |
| RBAC | 凭证最终能做什么 |
| NetworkPolicy | 凭证最终能访问哪里 |

gVisor 是运行时隔离，不替代这三类约束。

## 5. 第四条主链：Exec 为什么容易写错

阅读 internal/sandbox/exec.go 和 internal/api/handler.go。

真实链路：

~~~text
HTTP Exec 请求
  -> 解析有界 JSON argv
  -> client-go remotecommand
  -> WebSocket executor
  -> 仅传输/升级错误时 SPDY fallback
  -> stdout/stderr 有界 buffer
  -> 超时返回并删除 Sandbox
~~~

最关键的面试点：

- 命令 exit 7 是业务执行结果，不是传输失败，不能 fallback 重放；
- 已超时 context 不能继续用于 Delete；
- 输出必须在写入时限长，不能读完整内存后再截断；
- Agent 当前不直接获得通用 Exec，结构化诊断接口更窄。

## 6. 第五条主链：Kubernetes 诊断怎样经过 gVisor

阅读顺序：

1. internal/api/diagnostic_handler.go
2. internal/diagnostic/kubernetes.go
3. internal/diagnostic/summary.go
4. agentd/app/plugins/kubernetes.py
5. agentd/app/clients.py 的 SandboxdClient

链路：

~~~text
kubernetes_read Tool Call
  -> Python 参数策略
  -> KubernetesPlugin
  -> SandboxdClient
  -> Go diagnostic handler
  -> Go 根据 operation 构造固定 URL 和 argv
  -> pods/exec 进入 gVisor Pod
  -> projected SA 调 kube-apiserver
  -> RBAC 最终授权
  -> Go 压缩 PodList 后返回
~~~

模型不能提交 URL、Header、Token、kubeconfig 或任意 argv。Go 端必须重复验证，因为 Python 调用方可以被绕过。

## 7. 第六条主链：Plan 和审批门

阅读：

- internal/approval/types.go
- internal/approval/service.go
- internal/api/plan_handler.go

Propose：

1. 校验只允许固定 namespace 的 Deployment scale；
2. 限制 replicas；
3. 读取目标对象；
4. server-side dry-run；
5. 保存 diff、UID、resourceVersion；
6. 返回 pending Plan。

Approve：

1. 只接受 Operator Token；
2. pending 原子转 executing，阻止重复批准；
3. 重新读取目标；
4. 比较 UID 和 resourceVersion；
5. 使用当前 resourceVersion 执行 Update；
6. 成功或标记 stale/failed。

需要区分三个并发问题：

- UID 防同名对象删除重建；
- resourceVersion 防审批期间对象被修改；
- Update 本身的 resourceVersion 防复核后到写入间的竞争。

## 8. 第七条主链：agentd API 和 Worker

阅读：

1. agentd/app/main.py
2. agentd/app/store.py
3. agentd/app/runner.py
4. agentd/app/runtime/loop.py

main.py 负责：

- Alert Token 与 Agent API Token 分离；
- 流式读取并限制 Body；
- Alert 去重、Task/Trace/Session 查询；
- steer、follow-up、cancel、resume；
- Handler 快速返回，不同步等待模型。

TaskStore 负责：

- 有界内存队列；
- 单 Worker；
- taskId/sessionId/control/runtime task 的映射；
- 状态变化和 Trace 落盘；
- cancel 与 resume；
- 过期记录清理。

AgentRunner 负责 Sandbox 生命周期：

~~~text
claim
  -> 创建 ModelSession、PluginContext、FileWorkspace
  -> wait_for 执行 Agent Loop
  -> 生成可信 Trace
  -> release
  -> finally 中再次兜底
~~~

为什么 Sandbox 生命周期放 Runner 而不放某个 Tool：任何模型、插件和循环异常都必须经过同一个 finally。

## 9. 第八条主链：Pi-style 双层循环

阅读 agentd/app/runtime/loop.py 的顺序：

1. AgentLoopState
2. PiStyleAgentLoop.run
3. _prepare_context
4. _call_model
5. _validate_tools
6. _execute_tools
7. _finalize

先只看 run：

~~~text
while 外层：
    while 内层：
        应用 pending steer
        调模型
        有 Tool Call -> 校验并顺序执行
        Turn 结束后 drain steer
    自然结束后 drain follow-up
finalize
~~~

再看三个可信数据原则：

- 模型输出中的 evidence、deniedActions、planId 会被清空；
- 这些字段只从真实 ToolResult 和 Graph State 回填；
- ToolResult 的 modelContent 与 auditDetails 分开。

这说明最终结构化 JSON 不是“模型说了就信”，而是模型负责解释、程序负责执行事实。

## 10. 第九条主链：Plugin、Policy 和 ToolResult

阅读：

- plugins/base.py
- plugins/registry.py
- plugins/prometheus.py
- plugins/kubernetes.py
- plugins/linux_host.py
- plugins/files.py
- policy.py
- models.py

Plugin Registry 做三件事：

1. 显式注册仓库内内置插件；
2. 合并 Tool Schema 并检查重名；
3. 将 Tool 名分发到固定执行函数。

它不做动态扫描、不加载网络代码、不直接授予 Token。

Tool Call 的处理顺序：

~~~text
Schema 约束模型输出
  -> Python Policy 做前置拒绝
  -> Registry 解析工具归属
  -> Plugin/Client 执行
  -> ToolResult.modelContent 给模型
  -> ToolResult.auditDetails 给 Trace
~~~

## 11. 第十条主链：Session 与交互控制

阅读：

- runtime/control.py
- runtime/session.py
- store.py 的 send_control、cancel、resume

AgentControl 有两个 FIFO：

- steer queue：Turn 后安全点消费；
- follow-up queue：自然结束时消费。

SessionJournal 使用 append-only JSONL：

- Header：session 身份和初始告警摘要；
- Command：steer/follow-up/cancel；
- Transcript：脱敏消息快照；
- Result：任务结果。

Session 不保存 Header Token、模型隐藏思维、原始凭据和未经限制的大响应。

## 12. 第十一条主链：Linux Connector

阅读：

1. plugins/linux_host.py
2. clients.py 的 LinuxTargetConfig / LinuxHostClient
3. deploy/linux-target/sshd_config
4. deploy/linux-target/forced-command.sh
5. hack/run-linux-agent-demo.sh

模型只提交 targetId 和四选一 operation。地址、用户、端口、Key、known_hosts 均来自可信配置。

本地固定 argv 防本地 Shell 注入；远端 authorized_keys command 和 sshd ForceCommand 双重收口。SSH 路径不经过 gVisor。

## 13. 第十二条主链：文件工具

阅读：

1. agentd/app/tools/files.py
2. agentd/app/plugins/files.py
3. agentd/tests/test_files.py

FileWorkspace 的检查顺序：

~~~text
解析相对路径
  -> 拒绝绝对路径、..、NUL、超长层级
  -> 逐级 lstat 拒绝 symlink
  -> resolve 后确认仍在 task root
  -> 检查大小与文本编码
  -> expectedSha256 CAS
  -> 同目录临时文件 + os.replace
  -> 返回有界脱敏 diff
~~~

它仍有 lstat 到 open 之间的 TOCTOU 简化。生产方案可使用 openat2 和 RESOLVE_BENEATH/NO_SYMLINKS。
