# Prometheus 指标与轻量性能验证

## 1. 这个模块解决什么问题

只看 HTTP 201 或 Pod Running，只能知道“一次请求成功了”，不能回答：

- 预热池是否真的比冷启动快；
- 当前有多少 idle/busy 沙箱；
- 并发认领时是否发生过 CAS 冲突；
- Exec 花了多久、是否发生超时；
- 审批门主要拒绝了哪类请求。

本项目用少量 Prometheus 指标把这些关键机制暴露出来。目标是让 Demo 的设计结论可以被观察和验证，不搭建完整 Prometheus/Grafana 平台。

## 2. 项目里的最小实现

### 2.1 指标清单

| 指标 | 类型 | 用途 |
|---|---|---|
| `sandbox_acquire_seconds{source}` | Histogram | 比较 `pool` 与 `direct` 获取耗时 |
| `sandbox_pool_size{state}` | Gauge | 查看最近一次 Reconcile 统计的 idle/busy 数量 |
| `sandbox_claim_conflicts_total` | Counter | 观察 JSON Patch CAS 竞争 |
| `sandbox_exec_seconds` | Histogram | 观察远程命令执行耗时 |
| `sandbox_exec_timeouts_total` | Counter | 统计 Exec 超时或调用方取消 |
| `sandbox_plan_denied_total{reason}` | CounterVec | 统计审批门拒绝原因 |
| `sandbox_runtime_info{runtime}` | GaugeVec | 证明进程配置使用的 RuntimeClass |

`/metrics` 使用 Prometheus 官方 Go client 暴露文本格式。服务默认只监听 loopback，因此 Demo 没有额外给该端点加 Token。

### 2.2 为什么只用低基数 label

项目只允许：

- `source=pool|direct`；
- `state=idle|busy`；
- `reason` 为代码定义的有限集合；
- `runtime` 为进程启动配置。

绝不把 sandbox ID、Pod 名、命令文本或用户输入放进 label。每一种 label 组合都会形成一条时间序列，高基数会持续占用 Prometheus 内存，并拖慢查询。

### 2.3 指标在哪里更新

- `Manager.create`：成功得到 direct 沙箱后记录 acquire；
- `Pool.Claim`：CAS 成功后记录 pool acquire，CAS 失败时增加 conflict；
- `Pool.Reconcile`：基于 lister 快照更新 idle/busy Gauge；
- `Manager.Exec`：defer 记录总耗时，context 结束时增加 timeout；
- `main`：启动时写入配置的 runtime 信息；
- 审批门：拒绝 namespace、replicas、状态等请求时增加 denied。

只有成功获取到可用沙箱才计入 acquire。这样 Histogram 表示调用方真正获得沙箱所等待的时间，而不是一次失败尝试的内部耗时。

## 4. 必须掌握的八股知识

### Counter、Gauge、Histogram 有什么区别

- Counter 只增不减，适合请求数、错误数、冲突数；进程重启后可归零，查询时通常用 `rate()`；
- Gauge 可增可减，适合队列长度、池大小、当前并发；
- Histogram 在客户端按 bucket 累计次数，同时导出 `_sum` 和 `_count`，可在服务端聚合并计算分位数；
- Summary 在客户端直接计算 quantile，跨实例通常不能正确聚合，本 Demo 不需要它。

### Histogram 如何计算 P95

典型 PromQL：

```promql
histogram_quantile(
  0.95,
  sum by (le, source) (rate(sandbox_acquire_seconds_bucket[5m]))
)
```

`le` 是 bucket 上界。分位数是根据桶内分布估算，不是精确排序结果。

### 为什么指标不能证明 gVisor 实际运行

`sandbox_runtime_info{runtime="gvisor"} 1` 只证明 sandboxd 的配置，不证明 kubelet/containerd 真正选择了 runsc。真实运行证据仍然是节点 runtime handler 加 Pod 内 `dmesg` 的 `Starting gVisor...`。指标是配置证据，不能替代运行时证据。

### Pull 与 Push 模型

Prometheus 默认由服务端定期抓取 `/metrics`，应用不用知道 Prometheus 地址。短生命周期 batch job 才可能考虑 Pushgateway。sandboxd 是常驻 HTTP 服务，适合 pull。

### RED 与 USE 方法

- RED 面向服务：Rate、Errors、Duration；
- USE 面向资源：Utilization、Saturation、Errors。

本 Demo 的 acquire/exec duration、timeout/denied 接近 RED；pool size 和 conflict 用于解释内部容量与竞争。它不是完整生产监控体系。

## 5. 为什么采用当前方案

### 使用官方 client，而不是手拼文本

官方库能正确处理并发、Histogram bucket、OpenMetrics/Prometheus 编码与 Go runtime 默认指标。手拼文本看似少一个依赖，但容易出现竞态和格式错误。

### 使用全局默认 Registry

项目只有一个进程和一组固定 Collector，全局 Registry 最易读。生产项目或大量测试通常会把 `prometheus.Registry` 注入组件，以隔离测试和避免重复注册。

### 不在 Demo 中部署 Prometheus/Grafana

面试目标是理解指标设计与验证，而不是堆基础设施。直接 `curl /metrics` 已能证明埋点工作；如果需要展示图表，再外接 Prometheus 即可。

## 6. 真实验证结果

2026-08-18 在单节点 kind + gVisor + Calico 环境执行：

```text
Pool target: 2 Ready idle
Concurrent Claim: 5 requests, 5 unique IDs
Claim source: pool=2, direct=3
Release + reconcile: idle restored to 2
Metrics: runtime=gvisor, idle=2, busy=0, claim_conflicts=6
```

Manager/Exec 验证：

```text
Metrics: direct acquire=2, exec=3, timeout=1
```

这组数据证明了：

- 预热池容量确实为 2；
- 5 个并发 Claim 没有重复 ID；
- 池耗尽后 3 个请求走冷启动；
- JSON Patch `test` 在竞争中真实发生冲突并重试；
- 成功、非零退出和超时三次 Exec 都被统计；
- 超时计数为 1，且对应 Pod 已被清理。

这不是严格 benchmark。镜像缓存、WSL 调度、节点负载和样本数量都会影响延迟，不能拿这次结果宣称生产性能。

## 7. 本模块值得面试讲的坑

### Gauge 是控制器快照，不是强一致查询

`sandbox_pool_size` 在 Reconcile 中更新。HTTP Claim 刚返回时，informer 事件和下一轮 Reconcile 可能还没完成，此时 Gauge 短暂落后于 Kubernetes 对象。

验证脚本先等待 idle 恢复到 2，再读取指标。这体现了 informer/controller 的最终一致性，而不是指标实现错误。

### CAS 冲突数不应写成固定断言

5 个并发请求中本次观察到 6 次冲突，但 goroutine 调度和候选随机顺序会改变这个数字。脚本只断言指标存在和请求结果唯一，不要求冲突必须等于 6，避免把观测数据写成脆弱测试。

### `go get` 可能连带升级间接依赖

加入 Prometheus client 时，`x/net`、`x/sys`、protobuf 等间接依赖也发生了版本变化。不能只看新增的一行 direct dependency；必须审查 `go.mod/go.sum`，再跑 `go mod tidy`、单测、vet 和 build。

### `/metrics` 也有安全边界

指标可能泄露内部状态。本 Demo 依靠 `127.0.0.1` 默认监听限制暴露范围；如果改成集群服务或公网监听，应增加 NetworkPolicy、认证/TLS，或只允许监控命名空间抓取。

## 8. 面试高频问答

### Q：为什么 acquire 用 Histogram，不用 Gauge？

因为 acquire 是一次事件的耗时分布，需要 count、sum 和分桶来计算 P95/P99；Gauge 只能表示当前值，无法表达历史分布。

### Q：为什么不能把 Pod 名放 label？

Pod 名几乎每次都不同，会产生无界时间序列。日志适合查单个 Pod，指标适合聚合趋势；二者用途不同。

### Q：冲突多说明 CAS 方案错了吗？

不一定。CAS 冲突是乐观并发控制的正常反馈。需要结合获取延迟、fallback 比例和池容量判断；如果持续冲突严重，再考虑减少热点、改变候选选择或增大池，而不是取消原子校验。

### Q：如何监控池是否容量不足？

可比较 `source=direct` 与 `source=pool` 的 acquire rate/latency，同时观察 idle Gauge。direct 比例长期升高且 idle 常为 0，说明目标池容量可能偏小。

### Q：这个指标方案离生产还缺什么？

缺少独立 Registry、抓取鉴权/TLS、告警规则、仪表盘、持久化监控、跨副本聚合验证、SLO 和容量压测。Demo 有意不实现这些。
