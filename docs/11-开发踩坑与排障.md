# 开发踩坑与排障（持续维护）

> 这不是错误日志堆积，而是面试素材库。只记录具备迁移价值的坑：现象可复现、根因能解释、修复有证据，并且能体现工程判断。后续每个模块完成时都要检查是否有新条目需要加入。

## 怎么使用这份文档

面试讲坑时遵循五句话：

1. 我当时要实现什么；
2. 实际出现了什么现象；
3. 我如何缩小范围并找到根因；
4. 最终怎么修复、怎么验证；
5. 这件事让我形成了什么工程原则。

不要只说“版本不兼容”“网络有问题”，也不要编造未发生的故障。

## 1. 新版 gVisor 不再只有两个二进制文件

**现象**

旧教程只挂载 `runsc` 和 `containerd-shim-runsc-v1`。版本命令能运行，但新版真正创建容器时还可能找不到 Sentry sidecar。

**根因**

2026 年 7 月后的 gVisor 发布包改为多文件布局，`runsc` 会从相邻的 `gvisor-bin/` 启动 `gvisor_sentry`、`checkpointgofer` 等程序。

**解决与证据**

项目把 `runsc`、shim 和整个 `gvisor-bin/` 按相邻目录结构只读挂进 kind 节点。最终 Pod 内 `dmesg` 出现 `Starting gVisor...`，证明 sidecar 链路实际可用。

**面试可讲**

安装成功不等于运行路径成功；对运行时组件要验证完整制品布局和真实 workload，而不是只跑 `--version`。

## 2. WSL2 有 `/dev/kvm`，也不代表默认该选 KVM

**现象**

WSL2 环境能看到 `/dev/kvm`，容易直接推断 gVisor 应使用 KVM platform。

**根因**

WSL2 本身已在虚拟机中，KVM 路线依赖嵌套虚拟化是否完整开放；不同 Windows、WSL 内核和硬件配置差异大。

**解决与证据**

本 Demo 选择 gVisor 默认的 systrap，避免把秋招项目变成嵌套虚拟化排障项目。`runsc flags` 明确显示 systrap 为默认，真实 Pod 已跑通。

**面试可讲**

技术选择不是“理论性能最高”，而是结合运行环境、可复现性和项目目标做取舍。

## 3. 校验文件使用相对路径，执行目录不对会假失败

**现象**

本地已有 `gvisor.tar.bz2`，执行 `sha512sum -c /绝对路径/gvisor.tar.bz2.sha512` 却报告找不到 `gvisor.tar.bz2`。

**根因**

校验文件内部只记录相对文件名。`sha512sum -c` 相对当前工作目录查找目标，不会自动以校验文件所在目录为基准。

**解决与证据**

切换到下载目录后再校验，Go、kind、gVisor 均得到 OK。安装脚本进一步用明确文件路径和内置固定 hash，减少 cwd 依赖。

**面试可讲**

看到校验失败不能立刻判断下载损坏，要区分“摘要不一致”和“校验工具找错文件”。

## 4. kind 配置写的是旧 CRI 路径，节点实际是 containerd 2.x

**现象**

官方示例仍使用 `io.containerd.grpc.v1.cri` 配置路径，而 Kubernetes 1.35 kind 节点运行 containerd 2.2.0、配置 version 3。

**根因**

kind 接受兼容形式的 `containerdConfigPatches`，并在生成节点配置时迁移到 containerd 2.x 的 `io.containerd.cri.v1.runtime` 路径。只看输入模板无法确认最终结果。

**解决与证据**

创建节点后执行 `containerd config dump`，确认最终存在：

```toml
[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.runsc]
  runtime_type = 'io.containerd.runsc.v1'
```

**面试可讲**

声明式工具可能有转换层。排障时同时查看“期望配置、生成配置、运行行为”三层证据。

## 5. 有 RuntimeClass 对象不等于真的用了 gVisor

**现象**

`kubectl get runtimeclass` 和 PodSpec 都显示 gvisor，但它们只说明 API 对象存在和调度请求已声明。

**根因**

RuntimeClass 只是 handler 名称映射；节点 shim 缺失或配置错误时，Pod 可能失败。即便 Pod Running，也应验证容器看到的内核实现。

**解决与证据**

项目同时检查节点 containerd handler、挂载文件和 Pod 内 `dmesg`。只有出现 `[0.000000] Starting gVisor...` 才把 gVisor 标记为跑通。

**面试可讲**

区分配置证据和运行时证据，尤其是简历中声称使用了某个基础设施组件时。

## 6. kindnet 能联网，但不会执行 NetworkPolicy

**现象**

NetworkPolicy YAML 可以正常 apply，却可能完全没有拒绝流量。

**根因**

Kubernetes API 只保存策略；是否执行由 CNI 插件决定。kind 默认 kindnet 不支持 NetworkPolicy。

**解决与证据**

kind 配置关闭默认 CNI，安装 Calico。验收不是检查 policy 对象，而是让同一 Pod 访问 API 成功、访问 example.com 超时。

**面试可讲**

API 对象存在不代表数据面生效；网络、安全和存储功能都要找到真正的执行组件。

## 7. default-deny 后最容易漏掉 DNS

**现象**

所有域名请求都超时，看起来像应用、证书或整个网络坏了。

**根因**

egress default-deny 同样拦截到 CoreDNS 的 UDP/TCP 53。

**解决与证据**

单独允许 kube-system namespace 中带 `k8s-app=kube-dns` 标签的 Pod 53 端口，再通过 `kubernetes.default.svc` 实际解析和请求验证。

**面试可讲**

白名单网络要从依赖图出发：业务目标是访问 API，但前置依赖还包括 DNS、路由和 TLS CA。

## 8. NetworkPolicy 放行 Service ClusterIP 可能仍访问不了 API

**现象**

策略里允许 `kubernetes.default.svc` 的 ClusterIP，Pod 访问 API 仍可能超时。

**根因**

Service 请求经过 kube-proxy DNAT，策略执行点看到的目标可能已经是真实 endpoint。原生 ipBlock 也不能直接写 DNS 名称。

**解决与证据**

脚本从 EndpointSlice 动态读取 API Server 地址和端口，渲染成 `/32` allow 规则。实测 Pod 内请求返回 HTTP 200。

**面试可讲**

理解 Service 虚拟 IP、DNAT、endpoint 和策略执行时序，比背一份 YAML 更重要。

## 9. Kubernetes 1.35 应从 EndpointSlice 取后端

**现象**

使用 `kubectl get endpoints` 能工作，但每次出现 v1 Endpoints 已弃用警告。

**根因**

Kubernetes 1.33 起传统 Endpoints API 被标记 deprecated，EndpointSlice 是可扩展的替代 API。

**解决与证据**

脚本改用 `discovery.k8s.io/v1 EndpointSlice` 的 service-name label 查询，警告消失，仍得到本次 kind 的 `172.19.0.2:6443`。

**面试可讲**

遇到 deprecation 不只是“消警告”，还要理解新 API 解决了大规模 endpoint 对象过大的问题。

## 10. `kubectl auth can-i` 回答 no 时退出码也是 1

**现象**

验收脚本启用 `set -e` 后，只打印第一条允许结果，跑到预期拒绝用例就直接退出。

**根因**

`kubectl auth can-i` 输出 `no` 的同时返回非零退出码。对普通 shell 命令这是失败，但对负向权限测试，`no` 正是期望数据。

**解决与证据**

命令替换处使用 `|| true` 捕获文本，再显式比较 expected 与 actual。重跑后四条 yes/no 全部通过。

**面试可讲**

负向测试不能把所有非零退出码简单等同于测试失败；要区分“工具执行失败”和“系统按预期拒绝”。

## 11. server-side dry-run 也遵守对象依赖顺序

**现象**

namespace、SA、RBAC dry-run 都成功，但紧接着 dry-run Pod 报 ServiceAccount 不存在。

**根因**

server-side dry-run 会执行真实准入，但不会持久化前一个 dry-run 创建的 SA。因此后续 Pod 查不到它。

**解决与证据**

先实际幂等 apply SA，再对 Pod 做 server dry-run。安全 Pod 通过；故意缺少安全上下文的 Pod 被 PSA restricted 拒绝。

**面试可讲**

DryRun 的“像真实请求一样校验”和“不持久化”必须同时理解；多个相互依赖对象不能把一串 dry-run 当事务。

## 12. Pod Phase=Running 不等于业务 Ready

**现象**

容器已经 Running，但 readiness probe 可能尚未通过，立刻 exec 会失败或业务未初始化。

**根因**

Phase 描述生命周期大状态，Ready condition 才表示 Pod 是否可以接收流量和工作。

**解决与证据**

Manager 的 `WaitReady` 从 informer lister 读取并只接受 `PodReady=True`。单测构造 Running 但未 Ready 的 Pod，确认不会误判。

**面试可讲**

解释 Kubernetes status 时不要只看 phase；调度、容器启动、探针和 endpoint 就绪是不同阶段。

## 13. Exec fallback 不能对所有错误都重试

**现象**

如果 WebSocket 执行器遇到任意错误都 fallback 到 SPDY，命令返回非零退出码时可能被执行第二遍。

**根因**

远程执行错误既可能是协议升级失败，也可能是容器内命令真实失败。只有前者适合换协议重试。

**解决与证据**

fallback predicate 只接受 `IsUpgradeFailure` 或 `IsHTTPSProxyError`。命令 exit status 通过 `utilexec.ExitError` 原样返回，不重放命令。

**面试可讲**

重试机制必须判断操作是否幂等、错误发生在传输层还是业务层；盲目重试可能造成重复副作用。

## 14. 超时后的清理不能继续使用原 context

**现象**

Exec 因 deadline 到期返回后，如果拿同一个 ctx 删除 Pod，Delete 会立刻得到 context deadline exceeded，残留进程继续运行。

**根因**

context 一旦 Done 就不能“复活”；所有使用它的后续请求都会立即失败。

**解决与证据**

超时路径创建独立的 10 秒 cleanup context，精确删除该 Pod。超时沙箱不回池复用，因为其中可能残留子进程或污染状态。

**面试可讲**

请求 context 控制业务生命周期，补偿/清理动作通常需要独立、短时、受限的新 context。

## 15. WSL 测试要把资源门写进脚本

**现象**

kind、Calico、镜像拉取和并发 Pod 都可能消耗较多内存；依靠执行者“记得小心”不可重复。

**根因**

WSL 与 Windows 宿主共享资源，swap 抖动或磁盘暴涨会影响整个开发环境。

**解决与证据**

所有重操作先运行 `check-resources.sh`：可用内存低于 2 GiB 就停止；集群固定单节点，临时 Pod 有 CPU/内存 limit 并自动清理，默认并发 5。

**面试可讲**

工程安全不仅是应用权限，也包括开发和测试过程的资源边界、失败清理与影响范围。
