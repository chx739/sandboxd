# 开发踩坑与排障（持续维护）

> 这不是错误日志堆积，而是面试素材库。只记录具备迁移价值的坑：现象可复现、根因能解释、修复有证据，并且能体现工程判断。后续每个模块完成时都要检查是否有新条目需要加入。

## 怎么使用这份文档

面试讲坑时遵循五句话：

1. 我当时要实现什么；
2. 实际出现了什么现象；
3. 我如何缩小范围并找到根因；
4. 最终怎么修复、怎么验证；
5. 这件事让我形成了什么工程原则。

不要只说“版本不兼容”“网络有问题”，也不要编造未发生的故障。

## 1. 新版 gVisor 不再只有两个二进制文件

**现象**

旧教程只挂载 `runsc` 和 `containerd-shim-runsc-v1`。版本命令能运行，但新版真正创建容器时还可能找不到 Sentry sidecar。

**根因**

2026 年 7 月后的 gVisor 发布包改为多文件布局，`runsc` 会从相邻的 `gvisor-bin/` 启动 `gvisor_sentry`、`checkpointgofer` 等程序。

**解决与证据**

项目把 `runsc`、shim 和整个 `gvisor-bin/` 按相邻目录结构只读挂进 kind 节点。最终 Pod 内 `dmesg` 出现 `Starting gVisor...`，证明 sidecar 链路实际可用。

**面试可讲**

安装成功不等于运行路径成功；对运行时组件要验证完整制品布局和真实 workload，而不是只跑 `--version`。

## 2. WSL2 有 `/dev/kvm`，也不代表默认该选 KVM

**现象**

WSL2 环境能看到 `/dev/kvm`，容易直接推断 gVisor 应使用 KVM platform。

**根因**

WSL2 本身已在虚拟机中，KVM 路线依赖嵌套虚拟化是否完整开放；不同 Windows、WSL 内核和硬件配置差异大。

**解决与证据**

本 Demo 选择 gVisor 默认的 systrap，避免把秋招项目变成嵌套虚拟化排障项目。`runsc flags` 明确显示 systrap 为默认，真实 Pod 已跑通。

**面试可讲**

技术选择不是“理论性能最高”，而是结合运行环境、可复现性和项目目标做取舍。

## 3. 校验文件使用相对路径，执行目录不对会假失败

**现象**

本地已有 `gvisor.tar.bz2`，执行 `sha512sum -c /绝对路径/gvisor.tar.bz2.sha512` 却报告找不到 `gvisor.tar.bz2`。

**根因**

校验文件内部只记录相对文件名。`sha512sum -c` 相对当前工作目录查找目标，不会自动以校验文件所在目录为基准。

**解决与证据**

切换到下载目录后再校验，Go、kind、gVisor 均得到 OK。安装脚本进一步用明确文件路径和内置固定 hash，减少 cwd 依赖。

**面试可讲**

看到校验失败不能立刻判断下载损坏，要区分“摘要不一致”和“校验工具找错文件”。

## 4. kind 配置写的是旧 CRI 路径，节点实际是 containerd 2.x

**现象**

官方示例仍使用 `io.containerd.grpc.v1.cri` 配置路径，而 Kubernetes 1.35 kind 节点运行 containerd 2.2.0、配置 version 3。

**根因**

kind 接受兼容形式的 `containerdConfigPatches`，并在生成节点配置时迁移到 containerd 2.x 的 `io.containerd.cri.v1.runtime` 路径。只看输入模板无法确认最终结果。

**解决与证据**

创建节点后执行 `containerd config dump`，确认最终存在：

```toml
[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.runsc]
  runtime_type = 'io.containerd.runsc.v1'
```

**面试可讲**

声明式工具可能有转换层。排障时同时查看“期望配置、生成配置、运行行为”三层证据。

## 5. 有 RuntimeClass 对象不等于真的用了 gVisor

**现象**

`kubectl get runtimeclass` 和 PodSpec 都显示 gvisor，但它们只说明 API 对象存在和调度请求已声明。

**根因**

RuntimeClass 只是 handler 名称映射；节点 shim 缺失或配置错误时，Pod 可能失败。即便 Pod Running，也应验证容器看到的内核实现。

**解决与证据**

项目同时检查节点 containerd handler、挂载文件和 Pod 内 `dmesg`。只有出现 `[0.000000] Starting gVisor...` 才把 gVisor 标记为跑通。

**面试可讲**

区分配置证据和运行时证据，尤其是简历中声称使用了某个基础设施组件时。

## 6. kindnet 能联网，但不会执行 NetworkPolicy

**现象**

NetworkPolicy YAML 可以正常 apply，却可能完全没有拒绝流量。

**根因**

Kubernetes API 只保存策略；是否执行由 CNI 插件决定。kind 默认 kindnet 不支持 NetworkPolicy。

**解决与证据**

kind 配置关闭默认 CNI，安装 Calico。验收不是检查 policy 对象，而是让同一 Pod 访问 API 成功、访问 example.com 超时。

**面试可讲**

API 对象存在不代表数据面生效；网络、安全和存储功能都要找到真正的执行组件。

## 7. default-deny 后最容易漏掉 DNS

**现象**

所有域名请求都超时，看起来像应用、证书或整个网络坏了。

**根因**

egress default-deny 同样拦截到 CoreDNS 的 UDP/TCP 53。

**解决与证据**

单独允许 kube-system namespace 中带 `k8s-app=kube-dns` 标签的 Pod 53 端口，再通过 `kubernetes.default.svc` 实际解析和请求验证。

**面试可讲**

白名单网络要从依赖图出发：业务目标是访问 API，但前置依赖还包括 DNS、路由和 TLS CA。

## 8. NetworkPolicy 放行 Service ClusterIP 可能仍访问不了 API

**现象**

策略里允许 `kubernetes.default.svc` 的 ClusterIP，Pod 访问 API 仍可能超时。

**根因**

Service 请求经过 kube-proxy DNAT，策略执行点看到的目标可能已经是真实 endpoint。原生 ipBlock 也不能直接写 DNS 名称。

**解决与证据**

脚本从 EndpointSlice 动态读取 API Server 地址和端口，渲染成 `/32` allow 规则。实测 Pod 内请求返回 HTTP 200。

**面试可讲**

理解 Service 虚拟 IP、DNAT、endpoint 和策略执行时序，比背一份 YAML 更重要。

## 9. Kubernetes 1.35 应从 EndpointSlice 取后端

**现象**

使用 `kubectl get endpoints` 能工作，但每次出现 v1 Endpoints 已弃用警告。

**根因**

Kubernetes 1.33 起传统 Endpoints API 被标记 deprecated，EndpointSlice 是可扩展的替代 API。

**解决与证据**

脚本改用 `discovery.k8s.io/v1 EndpointSlice` 的 service-name label 查询，警告消失，仍得到本次 kind 的 `172.19.0.2:6443`。

**面试可讲**

遇到 deprecation 不只是“消警告”，还要理解新 API 解决了大规模 endpoint 对象过大的问题。

## 10. `kubectl auth can-i` 回答 no 时退出码也是 1

**现象**

验收脚本启用 `set -e` 后，只打印第一条允许结果，跑到预期拒绝用例就直接退出。

**根因**

`kubectl auth can-i` 输出 `no` 的同时返回非零退出码。对普通 shell 命令这是失败，但对负向权限测试，`no` 正是期望数据。

**解决与证据**

命令替换处使用 `|| true` 捕获文本，再显式比较 expected 与 actual。重跑后四条 yes/no 全部通过。

**面试可讲**

负向测试不能把所有非零退出码简单等同于测试失败；要区分“工具执行失败”和“系统按预期拒绝”。

## 11. server-side dry-run 也遵守对象依赖顺序

**现象**

namespace、SA、RBAC dry-run 都成功，但紧接着 dry-run Pod 报 ServiceAccount 不存在。

**根因**

server-side dry-run 会执行真实准入，但不会持久化前一个 dry-run 创建的 SA。因此后续 Pod 查不到它。

**解决与证据**

先实际幂等 apply SA，再对 Pod 做 server dry-run。安全 Pod 通过；故意缺少安全上下文的 Pod 被 PSA restricted 拒绝。

**面试可讲**

DryRun 的“像真实请求一样校验”和“不持久化”必须同时理解；多个相互依赖对象不能把一串 dry-run 当事务。

## 12. Pod Phase=Running 不等于业务 Ready

**现象**

容器已经 Running，但 readiness probe 可能尚未通过，立刻 exec 会失败或业务未初始化。

**根因**

Phase 描述生命周期大状态，Ready condition 才表示 Pod 是否可以接收流量和工作。

**解决与证据**

Manager 的 `WaitReady` 从 informer lister 读取并只接受 `PodReady=True`。单测构造 Running 但未 Ready 的 Pod，确认不会误判。

**面试可讲**

解释 Kubernetes status 时不要只看 phase；调度、容器启动、探针和 endpoint 就绪是不同阶段。

## 13. Exec fallback 不能对所有错误都重试

**现象**

如果 WebSocket 执行器遇到任意错误都 fallback 到 SPDY，命令返回非零退出码时可能被执行第二遍。

**根因**

远程执行错误既可能是协议升级失败，也可能是容器内命令真实失败。只有前者适合换协议重试。

**解决与证据**

fallback predicate 只接受 `IsUpgradeFailure` 或 `IsHTTPSProxyError`。命令 exit status 通过 `utilexec.ExitError` 原样返回，不重放命令。

**面试可讲**

重试机制必须判断操作是否幂等、错误发生在传输层还是业务层；盲目重试可能造成重复副作用。

## 14. 超时后的清理不能继续使用原 context

**现象**

Exec 因 deadline 到期返回后，如果拿同一个 ctx 删除 Pod，Delete 会立刻得到 context deadline exceeded，残留进程继续运行。

**根因**

context 一旦 Done 就不能“复活”；所有使用它的后续请求都会立即失败。

**解决与证据**

超时路径创建独立的 10 秒 cleanup context，精确删除该 Pod。超时沙箱不回池复用，因为其中可能残留子进程或污染状态。

**面试可讲**

请求 context 控制业务生命周期，补偿/清理动作通常需要独立、短时、受限的新 context。

## 15. WSL 测试要把资源门写进脚本

**现象**

kind、Calico、镜像拉取和并发 Pod 都可能消耗较多内存；依靠执行者“记得小心”不可重复。

**根因**

WSL 与 Windows 宿主共享资源，swap 抖动或磁盘暴涨会影响整个开发环境。

**解决与证据**

所有重操作先运行 `check-resources.sh`：可用内存低于 2 GiB 就停止；集群固定单节点，临时 Pod 有 CPU/内存 limit 并自动清理，默认并发 5。

**面试可讲**

工程安全不仅是应用权限，也包括开发和测试过程的资源边界、失败清理与影响范围。

## 16. Pool Gauge 是最终一致快照，不是强一致查询

**现象**

Claim 或 Release 刚完成时立刻抓取 `/metrics`，`sandbox_pool_size` 可能暂时仍是旧值。

**根因**

Gauge 由单 worker Reconcile 基于 informer/lister 快照更新；API 请求、对象事件、缓存同步和下一轮协调存在正常时间差。

**解决与证据**

验收先等待 Kubernetes 中的 idle Pod 收敛，再读取指标。本次最终得到 `idle=2,busy=0`，并确认释放后池容量恢复。

**面试可讲**

基于 informer 的控制器天然是最终一致模型。观测和测试必须理解数据的新鲜度，不能把短暂旧值误判为业务错误。

## 17. CAS 冲突指标不能写死成固定数字

**现象**

本次 5 并发认领观察到 6 次 JSON Patch `test` 冲突，但重复运行不保证仍等于 6。

**根因**

goroutine 调度、API Server 时序和随机候选顺序都会改变竞争过程。冲突是乐观并发控制的正常反馈，不是确定性业务输出。

**解决与证据**

脚本严格断言 5 个 ID 唯一、pool/direct 路径都发生、冲突 Counter 可读取，但不固定冲突次数。

**面试可讲**

测试应锁住业务不变量，把调度相关数值作为观测信号；否则并发测试容易变成 flaky test。

## 18. 新增一个 Go 依赖可能连带升级整条依赖图

**现象**

加入 Prometheus Go client 后，`x/net`、`x/sys`、protobuf 等多个 indirect dependency 同时变化。

**根因**

Go module 使用最小版本选择；新模块的最低版本要求可能把构建列表中的共享依赖整体抬高。

**解决与证据**

审查 `go.mod/go.sum` 的完整 diff，并重新执行 `go mod tidy`、`go test ./...`、`go vet ./...` 和 `go build ./...`，全部通过后才接受变更。

**面试可讲**

依赖升级的审查单位不是一行 direct dependency，而是最终 build list 和回归证据。

## 19. client-go fake 默认不会模拟 server-side DryRun

**现象**

测试调用带 `DryRunAll` 的 Update 后，fake tracker 中的 Deployment replicas 竟然已经变化。

**根因**

client-go fake 主要记录和分发 action，不等价于真实 API Server，也不会自动实现 dry-run“不持久化”的语义。

**解决与证据**

测试 reactor 检查 `UpdateOptions.DryRun`：DryRun 请求只返回对象副本，不更新 tracker；普通 Approve Update 才交给默认 reactor。连续 20 轮测试通过。

**面试可讲**

mock/fake 只能模拟明确实现的行为；测试基础设施与生产组件之间的语义差异本身也需要验证。

## 20. DryRun 成功不是资源预留，也不是永久通行证

**现象**

Propose 已通过 server-side DryRun，但在批准前修改 Deployment annotation 后，旧 Plan 不应继续执行。

**根因**

DryRun 不写 etcd、不锁对象，也不冻结配额和准入配置；check 与 use 之间始终存在时间窗口。

**解决与证据**

Plan 保存 UID/resourceVersion，Approve 前重新 GET 对比；版本变化返回 409 并标记 stale。本次实测 replicas 保持 1。

**面试可讲**

预检查只能降低失败概率，不能替代执行时的并发控制和重新授权/校验。

## 21. 只比较 namespace/name 防不住对象被删除重建

**现象**

同名 Deployment 看起来仍存在，但它可能已经被删除后重新创建，旧审批不应应用到新对象。

**根因**

Kubernetes 名字可以复用，UID 才标识对象生命周期；resourceVersion 标识同一对象的具体存储版本。

**解决与证据**

Plan 同时保存并比较 UID 和 resourceVersion，Update 继续携带 resourceVersion 使用 API Server 乐观锁。

**面试可讲**

对象身份和对象版本是两个维度：UID 防替身，resourceVersion 防并发修改。

## 22. Plan 状态检查与执行之间也有并发窗口

**现象**

若两个 Operator 请求都先读到 pending，它们可能同时向 API Server 执行同一个 Plan。

**根因**

“检查 pending，再执行”是典型 check-then-act 竞态；普通读锁不能把两个步骤变成原子操作。

**解决与证据**

在 mutex 下先把 pending 改为 executing，再释放锁访问 API Server。第二个 approve 看到非 pending 后返回 409；临时 API 错误则恢复 pending。

**面试可讲**

外部 API 调用不应长时间持有进程锁，但本地状态必须先原子抢占；这是两阶段状态机的最小形式。

## 23. cleanup 注册在 context 校验之前可能删错集群

**现象**

验证脚本使用普通 `kubectl`，如果用户切换到其他 context 后运行，创建和退出清理都可能命中错误集群。

**根因**

脚本默认继承当前 kubeconfig context；仅靠资源名称和 label 不能证明目标就是本地 Demo 集群。若先注册 trap，后续前置检查失败时 trap 仍可能执行删除。

**解决与证据**

所有写脚本在注册 cleanup 前先要求 `context=kind-sandboxd`、kind cluster 存在且节点精确为单节点 `sandboxd-control-plane`。完整 Demo 首行输出该证据。

**面试可讲**

自动清理本身也是破坏性操作；必须先验证环境身份，再注册或执行补偿逻辑。

## 24. 同一 Namespace 出现在多份 apply 清单会产生字段所有权风险

**现象**

gVisor smoke 清单和安全清单都声明 `sandboxd-demo` Namespace，其中一份没有 PSA labels。

**根因**

client-side/server-side apply 都会维护字段归属或 last-applied 状态。多个清单以相同管理者反复声明同一对象，可能删除、覆盖或争抢另一份清单维护的字段。

**解决与证据**

Namespace 只由 `deploy/namespace.yaml` 管理，smoke 清单只包含 Pod；`verify-gvisor.sh` 显式先应用带 PSA 的 Namespace。完整 Demo 后复查 enforce label 仍为 `restricted`。

**面试可讲**

声明式配置也需要清晰的对象所有权。不要把共享基础对象复制到每个 workload 清单中。

## 25. WSL 文件能执行，不代表 Git 保存了可执行位

**现象**

本机可以直接运行 `./hack/demo.sh`，但 `git ls-files -s` 显示所有脚本模式仍是 `100644`；Linux 新 clone 会得到 permission denied。

**根因**

仓库位于 Windows DrvFS 挂载，文件权限呈现与 Git index mode 不是一回事；同时 `core.filemode=false` 会忽略普通 chmod 变化。

**解决与证据**

使用 `git update-index --chmod=+x hack/*.sh` 显式把全部脚本记录为 `100755`，再用 `git ls-files -s` 审计索引，而不是只看 `stat`。

**面试可讲**

可复现性要检查版本控制中真正提交的元数据；本机文件系统行为不能替代 clone 后验证。

## 26. WSL 有 Python 不代表能直接使用 pip

**现象**

Python 3.12.3 可以运行，但 python3 -m pip 报 No module named pip。为了安装 Agent 依赖而直接 sudo apt install 会扩大系统修改范围。

**根因**

Ubuntu 将解释器、venv 和 pip 拆分管理；同时本机已经存在用户目录中的 uv，只是旧计划没有先检查。

**解决与证据**

先检查 python3、venv、pip 和 uv。最终选择已有用户态 uv，在 agentd/.venv 管理环境，并用 pyproject.toml + uv.lock 固定依赖，不修改系统 Python。

**面试可讲**

可复现构建不仅是写 requirements；还要区分系统解释器与项目环境，并避免让 Demo 的安装流程污染宿主机。

## 27. 禁用 LangSmith 功能不等于依赖树中没有 langsmith

**现象**

uv 解析 LangGraph、langchain-core 和 langchain-openai 后，依赖树仍包含 langsmith。

**根因**

langsmith 是 LangChain Core 的传递依赖；是否安装和是否启用外部 tracing 是两个不同问题。

**解决与证据**

保留框架所需传递依赖，但不配置 LangSmith API Key，显式关闭 tracing，不调用 LangSmith Client，并在秘密扫描和网络证据中确认没有 Trace 上传。

**面试可讲**

供应链依赖、运行时配置和数据外发是三个层次。仅说“我没主动用某 SDK”不能证明敏感数据不会离开系统。

## 28. Agent 工具白名单不能保护后端通用 Exec

**现象**

Python Agent 可以只注册只读工具，但现有 sandboxd 仍暴露接收任意 argv 的通用 Exec API。如果把 Python 校验称为最终边界，攻击者绕过 agentd 后就能跳过这层。

**根因**

Tool Schema 和 LangGraph Policy 属于调用方约束，不是服务端授权；安全策略放在不可信调用方内，天然可以被绕过。

**解决与证据**

新增 Go 结构化 Kubernetes Diagnostic API。模型只能提交五种读操作和受限参数，Go 生成固定 URL/argv；危险 operation 和错误 namespace 在接触 Manager 前返回 403 和 denyLayer=tool-policy。通用 Exec 保留，用于继续验证 RBAC 最终拒绝。

**面试可讲**

安全检查必须位于无法被调用者绕开的信任边界。前端隐藏按钮、Prompt 白名单和 Agent Tool Schema 都不能替代服务端授权。

## 29. 为只读排障安装 kubectl 会扩大镜像和命令面

**现象**

旧 Agent 计划默认在沙箱中运行 kubectl，但当前最小镜像只有 curl。为了一个 Demo 安装 kubectl 会增加镜像、版本和可执行命令面。

**根因**

kubectl 只是 Kubernetes API Client，不是读取集群的必要条件；真正的身份来自 projected ServiceAccount Token，授权来自 API Server RBAC。

**解决与证据**

Go 将结构化操作映射为固定 Kubernetes HTTPS GET 路径，在 gVisor 内由 curl 使用短时 Token 和 CA 发起请求。模型不能传 URL、Header、Token 或 argv，名称只作为校验并编码后的 URL 段。

**面试可讲**

最小权限不只包含 RBAC，也包括工具和镜像能力。能用窄协议完成的功能，不应暴露通用 CLI。

## 30. 读取完整 HTTP Body 后再判断大小不是真正的限流

**现象**

最初的 FastAPI Handler 使用 await request.body()，随后才检查是否超过 64 KiB。状态码虽然能返回 413，但超大 Body 已经进入内存。

**根因**

事后检查只能限制业务处理，不能限制接收阶段的内存占用；Content-Length 也可能缺失或不可信。

**解决与证据**

先快速检查 Content-Length，再通过 request.stream() 分块累计，每收到一块都检查总长度，超过上限立即停止并返回 413。

**面试可讲**

限制输入大小必须发生在资源消耗之前。日志截断、上传限制和响应上限都应采用同样的流式边界思路。

## 31. 模型一次返回多个 Tool Call 时必须逐个闭合协议

**现象**

只执行第一条 Tool Call 看起来更简单，但下一轮消息历史里其余 tool_call_id 没有对应 ToolMessage，部分 OpenAI-compatible Provider 会直接拒绝请求。

**根因**

Tool Calling 不只是函数调用列表，也是严格的消息协议；每个模型产生的 Tool Call 都需要对应结果。

**解决与证据**

validate_tools 对本轮所有 Tool Call 逐个校验并计数，execute_tools 为每个 id 返回一个 ToolMessage；超出白名单或次数的调用也返回明确 denied Observation，而不是丢弃。

**面试可讲**

Agent Runtime 要同时维护业务状态和模型协议状态。安全拒绝也必须以合法协议消息反馈，否则边界正确但对话无法继续。

## 32. 在子目录测试通过不代表仓库根目录能导入

**现象**

在 agentd 目录运行 unittest 全部通过，但从仓库根目录执行 uv run --project agentd 时，测试报 ModuleNotFoundError: app。

**根因**

测试最初把 app 当作顶层包，实际导入结果依赖当前工作目录被加入 sys.path；本地命令和 CI 命令的工作目录不同。

**解决与证据**

增加 agentd 包入口，统一使用 agentd.app 绝对导入；README、测试和 Uvicorn factory 命令全部从仓库根目录执行。根目录 frozen 测试随后通过。

**面试可讲**

可复现性包含启动目录、模块搜索路径和打包边界。只在 IDE 或某个 cwd 下成功的 Python 项目不算真正可运行。

## 33. 确定性演示告警不能冒充真实异常检测

**现象**

为了让面试 Demo 每次都能触发告警，规则使用 vector(1)。如果 README 直接称其为 CrashLoop 检测，会把“告警传输验证”和“故障检测能力”混为一谈。

**根因**

真实 Kubernetes 状态指标通常需要 kube-state-metrics，会增加镜像、资源和安装成本；本项目当前重点是外部告警到安全诊断的完整链路。

**解决与证据**

规则注释和文档明确标记 deterministic demo alert；Prometheus 真实计算规则并把 firing 告警交给 Alertmanager，但不宣称表达式检测了 Pod 状态。故障真实性由 restricted gVisor CrashLoop Fixture 单独证明。

**面试可讲**

Demo 可以替换触发源以控制成本，但必须明确哪些部件是真实的、哪些输入是确定性 Fixture。证据边界比堆组件更重要。

## 34. kubectl 的 client dry-run 仍可能依赖在线 API discovery

**现象**

kind API Server 停止后执行 kubectl create --dry-run=client --validate=false -f，仍然尝试访问旧 kubeconfig 地址并因连接拒绝而失败。

**根因**

client dry-run 避免提交对象，却不保证完全离线；处理通用 YAML 时 kubectl 仍可能通过 RESTMapper discovery 确定 Group、Version 和 Resource。

**解决与证据**

离线阶段先使用 promtool/amtool 和脚本语法检查；Kubernetes 清单的资源映射与准入语义留到 M4 临时集群启动后验证，不为一次离线检查放宽环境或伪造成功证据。

**面试可讲**

“不写入服务端”和“完全不依赖服务端”是两个概念。测试计划应区分纯语法检查、客户端生成、服务端 DryRun 和真实创建。

## 35. 原始 PodList 进入 Agent 上下文会先把 JSON 截断

**现象**

Replay 需要从 list_pods 的 Observation 取得 Deployment 生成的动态 Pod 名，但完整 PodList 含 PodSpec、状态和元数据，容易超过 4 KiB 上限；简单截断会让 JSON 无法解析。

**根因**

传输层 64 KiB 上限与模型上下文 4 KiB 上限解决的是不同问题。即使响应未超过 HTTP 限制，也不代表适合直接作为 Tool Observation。

**解决与证据**

在可信 Go Diagnostic 边界解析 PodList，只返回最多 20 个 Pod 的 name、phase、restartCount；Python 只从合法 ToolMessage JSON 解析名称，随后仍经过 DNS 名称与工具策略校验。真实链路中的摘要保持有效 JSON 并成功定位动态 Pod。

**面试可讲**

工具输出应在可信侧做语义压缩，而不是把原始 API 对象塞给模型。这样同时降低 Token 成本、截断风险和 Prompt Injection 面。

## 36. gVisor 下 previous log 返回 HTTP 成功也可能没有业务日志

**现象**

第一次真实 Replay 等到 restartCount 大于 0 后请求 previous=true，Kubernetes API 和 curl 都返回成功，但 stdout 是 unable to retrieve container logs for containerd://...，注入文本没有进入 Trace。

**根因**

HTTP/命令成功只说明请求完成，不保证返回内容满足诊断语义；gVisor、containerd 与快速 CrashLoop 组合下，上一实例日志可能已无法按 previous 路径读取。

**解决与证据**

Fixture 就绪条件改为 kubectl 实际读到当前日志中的注入标记，Replay 使用 previous=false；第二次真实运行 injectedVia=podlog、verdict=contained。脚本没有删除断言或把 Replay 自报的 injectionDetected 当成真实输入证据。

**面试可讲**

端到端验证必须断言业务语义，不能只看 HTTP 200 或进程退出码。失败的第一轮证据帮助区分“模型说看到了”和“Trace 证明上下文真的包含”。
