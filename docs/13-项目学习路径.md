# 项目学习路径

> 面向本仓库作者自学与面试复习。代码是在 AI 辅助下写出来的，**这份文档的目的是把它变成真正属于你的理解**。
> 前置：已完成 Linux 隔离原语、runc、RBAC、informer 等概念学习。

## 两条核心方法

**一、先读代码，再读文档。**

先读文档会产生「我懂了」的错觉——文档是解释性的、顺畅的、已经消化过的。先读代码会暴露真实困惑，这时文档才从「灌输」变成「回答我的问题」。文档没回答的那部分，才是你真正要补的。

每个模块的动作固定为：**读代码 → 写下困惑 → 读对应文档 → 检查是否被回答**。

**二、破坏优于阅读。**

被动阅读建立不了归属感。改一个字段、预测后果、跑、验证、恢复——**破坏一次的理解深度超过读十遍**。阶段 3 是整条路径的核心。


Phase 2 再增加约 4–6 小时：先读 Agent 图和策略，再跑一次完整 Replay，最后用面试问答自测。

## 阶段 1 · 文档阅读（约 4.5 小时）

- `docs/00-实现计划.md` — 快扫，建立模块地图

- **`docs/10-面试问答与项目讲法.md`** — 用**自测**代替阅读。遮住答案自己答，答完对照。读十遍不如自测两遍。

### D 类 · 查证，不通读

`docs/evidence/phase0-8` 的用途是**对答案**：阶段 2 跑脚本时先自己解释输出，再翻对应 evidence 核对。不要当教材读。

**另注**：`docs/12-Agent层实现计划.md` 是 Phase 2 权威规格。先用它确认边界，再读 14 的实际实现；DeepSeek Live 与 Replay 已分别实测，仍不能把两类证据混为一谈。

## 阶段 3 · 破坏实验（全天，核心）

### 安全前提（每次都要遵守）

```bash
git switch -c learn/experiments      # 专用分支，不在主分支改
git status                           # 开始前确认干净
```

- 每个实验**结束立刻恢复**：`git checkout -- .`（代码）或重新 apply 原 YAML（集群）
- 只影响 `sandboxd-demo` / `sandboxd-target` 两个 namespace，不碰其他资源
- 开始前跑 `./hack/check-resources.sh`；内存紧张就不要并行做
- **先写下预测，再执行。预测错的地方就是你真正的知识缺口。**

### 实验总览

| # | 改动 | 验证的是 | 优先级 |
|---|---|---|---|
| 1 | 删掉 `claimPatch` 的 `test` op | CAS 存在的理由 | **必做** |
| 2 | 注释掉 `resourceVersion` 比较 | TOCTOU 防护防住了什么 | **必做** |
| 3 | 删掉 `automountServiceAccountToken: false` | 权限模型如何无声漏掉 | 高 |
| 4 | 删掉 NetworkPolicy 的 `allow-dns` | 「最常见事故」的真实手感 | 高 |
| 5 | `readOnlyRootFilesystem` 改 false | PSA 双层防御是否真生效 | 中 |
| 6 | 删掉 projected volume 的 `ca.crt` | 为什么必须手动挂三样 | 中 |
| 7 | `WaitReady` 改成只看 `phase == Running` | Running ≠ Ready 的后果 | 中 |
| 8 | 去掉 exec 的输出上限 | 为什么 observation 必须截断 | 低 |

实验 1 和 2 对应简历最亮的两点，**不能砍**。

### 实验 1 · 删掉 CAS 的 test 操作（必做）

**改**：`internal/sandbox/pool.go` 顶部的 `claimPatch`，删掉 `test` 那一行，只留 `replace`。

**预测**：5 个并发 Claim 会发生什么？

**执行**：
```bash
go build ./... && ./hack/verify-pool.sh
```

**观察**：脚本里的「唯一 ID」断言是否失败，即多个请求是否认领到同一个沙箱。同时看 `sandbox_claim_conflicts_total` 是否变成 0——**没有冲突不代表没有竞争，代表竞争没被发现**。

**这个实验的价值**：它把「JSON Patch test 实现 CAS」从一句话变成了你亲眼见过的故障。

**恢复**：`git checkout -- internal/sandbox/pool.go && go build ./...`

### 实验 2 · 注释掉 resourceVersion 比较（必做）

**改**：`internal/approval/service.go` 的 `Approve()` 里那段
```go
if string(current.UID) != plan.TargetUID || current.ResourceVersion != plan.TargetResourceVersion {
    return s.markStale(id)
}
```
改成只比 `UID`，去掉 `ResourceVersion` 那半边条件。

**预测**：如果 plan 提交后目标被别人改了，approve 会怎样？

**执行**（手工制造 TOCTOU）：
```bash
go build ./...
kubectl apply -f deploy/smoke/approval-target.yaml     # 建目标 Deployment
# 1. 提交 plan（记下返回的 planID 和 diff）
# 2. 手动改动目标，制造 stale：
kubectl scale deployment/<name> -n sandboxd-target --replicas=5
# 3. 再 approve 那个 planID
```

**观察**：它是否**基于过期的 diff 执行了写入**，把别人刚改的 5 覆盖掉。对照未修改版本应返回 `stale` + `409`。

**这个实验的价值**：面试问「dry-run 到 approve 之间对象变了怎么办」，你答的是亲手复现过的故障，不是背的机制。

**恢复**：
```bash
git checkout -- internal/approval/service.go && go build ./...
kubectl delete -f deploy/smoke/approval-target.yaml --ignore-not-found
kubectl delete namespace sandboxd-target --ignore-not-found
```

### 实验 3 · 删掉 automountServiceAccountToken: false

**改**：`internal/sandbox/spec.go` 里把 `AutomountServiceAccountToken` 那一行从 PodSpec 移除。

**预测**：容器内 `/var/run/secrets/kubernetes.io/serviceaccount/` 会变成什么？你手动挂的 projected volume 和自动挂载会冲突还是覆盖？

**执行**：
```bash
go build ./... && ./hack/verify-manager.sh
# 另开终端，进沙箱看挂载：
kubectl exec -n sandboxd-demo <pod> -- ls -la /var/run/secrets/kubernetes.io/serviceaccount/
kubectl exec -n sandboxd-demo <pod> -- cat /var/run/secrets/kubernetes.io/serviceaccount/namespace
```

**观察**：token 是哪个 SA 的、有没有 `expirationSeconds`（自动挂载的没有短时效控制）。**这就是「权限模型无声漏掉」的具体形态**——没有报错，只是安全性静默降级。

**恢复**：`git checkout -- internal/sandbox/spec.go && go build ./...`

### 实验 4 · 删掉 allow-dns 策略

**改**：不改代码，直接删集群里的策略。
```bash
kubectl delete networkpolicy sandbox-allow-dns -n sandboxd-demo
```

**预测**：沙箱内 `kubectl get pods` 会**立即报错**，还是**卡住直到超时**？

**执行**：
```bash
./hack/verify-manager.sh    # 或直接在已有沙箱里 exec
kubectl exec -n sandboxd-demo <pod> -- kubectl get pods -n sandboxd-demo
```

**观察**：现象是**超时**而不是「网络被拒绝」。这就是为什么这类事故难排查——**看起来像服务挂了，不像策略问题**。再试 `nslookup kubernetes.default` 确认是解析失败而非连接失败。

**恢复**：
```bash
./hack/apply-security.sh    # 重新应用完整策略
kubectl get networkpolicy -n sandboxd-demo    # 确认三条都在
```

### 实验 5 · readOnlyRootFilesystem 改 false

**改**：`internal/sandbox/spec.go` 里 `readOnlyRootFilesystem := true` 改成 `false`。

**预测**：Pod 会正常创建（只是安全性下降），还是**创建就被拒绝**？

**执行**：`go build ./... && ./hack/verify-manager.sh`

**观察**：namespace 开了 `pod-security.kubernetes.io/enforce: restricted`，所以这里应该看到**准入阶段被拒**，错误信息里会点明违反了 restricted 的哪一项。

**这个实验的价值**：它现场证明了「双层防御」不是说法——PodSpec 是第一层，PSA 在 API Server 准入阶段是第二层，代码被改坏时第二层仍然拦住。

**恢复**：`git checkout -- internal/sandbox/spec.go && go build ./...`

### 实验 6 · 删掉 projected volume 里的 ca.crt

**改**：`internal/sandbox/spec.go` 的 projected volume sources 里，删掉那个 `ConfigMap` 投射（`kube-root-ca.crt` 的 `ca.crt`）。

**预测**：容器内 kubectl 会报什么错？

**执行**：`go build ./... && ./hack/verify-manager.sh`，然后在沙箱内跑 kubectl。

**观察**：报的是证书验证失败（`x509: certificate signed by unknown authority` 一类），不是权限错误。**这解释了为什么手动挂载必须挂三样**：token 解决「我是谁」，ca.crt 解决「我信不信 apiserver」，namespace 解决「我在哪」。少任何一样 in-cluster 配置都不完整。

**恢复**：`git checkout -- internal/sandbox/spec.go && go build ./...`

### 实验 7 · WaitReady 只看 phase == Running

**改**：`internal/sandbox/manager.go` 的 `WaitReady`，把 `PodReady` condition 判断改成只检查 `pod.Status.Phase == corev1.PodRunning`。

**预测**：Create 返回后立刻 exec，会成功还是失败？

**执行**：`go build ./...`，然后连续跑几次 `./hack/verify-manager.sh`。

**观察**：可能间歇性失败（容器进程还没起来就 exec）。**注意这类问题是概率性的**——跑一次成功不代表没问题，这本身就是个重要认知：`Running` 只说明容器被创建了，`Ready` 才说明它能服务。

**恢复**：`git checkout -- internal/sandbox/manager.go && go build ./...`

### 实验 8 · 去掉 exec 输出上限

**改**：`internal/sandbox/exec.go` 里的输出字节上限调到很大或去掉。

**预测**：拉一个大日志会发生什么？

**执行**：在沙箱内 `kubectl logs` 一个日志量大的 Pod（可以先造一个疯狂打日志的 Pod 在 `sandboxd-target`）。

**观察**：响应体量级、内存占用、以及如果接了 LLM 这段输出会消耗多少 context。**这解释了为什么 Agent 层的 observation 必须截断**——不是为了美观，是成本和稳定性问题。

**恢复**：`git checkout -- internal/sandbox/exec.go && go build ./...`，并清理造的日志 Pod。

### 全部实验结束后

```bash
git switch agent/environment-gvisor    # 回到原分支
git branch -D learn/experiments        # 删掉实验分支
./hack/apply-security.sh               # 确认策略完整
./hack/check-resources.sh              # 确认无残留、资源正常
kubectl get pods -n sandboxd-demo      # 应无残留 managed Pod
```

## 检验标准

### 第一档 · 文档读完了

不看文档回答：

1. `GOAL.md` 里明确「不做」的有哪些，为什么每一条都不做？

3. `approval.Approve()` 有几条返回路径，`markStale` 在哪两种情况触发？

### 第二档 · 代码归你了

**不看代码画出 `Claim()` 的完整流程图**，必须包含：
- 从 lister 取候选到 CAS patch 的路径
- CAS 失败（422）后的分支
- 候选全部失败或池为空时降级到 direct create 的路径
- 认领成功后为什么要 `queue.Add(poolKey)`

画得出来这个模块就归你了。画不出来回去读 `pool.go` 的 `Claim`。

同样对 `approval.Approve()` 做一遍。

- 30 秒介绍脱稿，不超时

## 一个诚信提醒

`docs/11` 的 36 条坑是开发过程中记录的。表述时用「这是我在开发过程中遇到并记录的问题」，**不要说成「我调试了三天」**。

面试官在意的是你能否解释根因，不在意你花了几小时。但如果夸大过程又答不出细节，那是两个问题叠加，比不夸大糟得多。
