# 工作区恢复性能与流量测量

规格以[43](43-工作区持久化与恢复实施约束-NFS-v1与restic-MinIO-v2.md)为准。本文记录Phase9的小规模本机实验，不外推生产QPS/SLA。V2仍以NFS为运行工作区，后续比较应复用同一负载，增加同步restic检查点等待；不能预先宣称日常I/O更快。

## 1. 两条可重复入口

```bash
bash hack/workspace.sh entry --output .cache/entry-result.json
bash hack/workspace.sh benchmark --repeats 3 --output .cache/nfs-benchmark.json
```

前者实际调用统一入口的go/agent子命令：Go绑定8080、agentd绑定8090，固定Replay；第一进程完成文件写入、第二次模型响应尚未返回时，强杀自己的agentd并原目录重启。后者使用10880直接测Go受限文件接口，要求项目工作区命名空间没有其他Pod。两者串行，凭据为仅本夹具使用的合成身份，不读取真实Key、不调用付费模型；业务文件和控制目录保留，Pod由Go正常释放。

构建与安装依赖沿用仓库固定Go1.26.5、Python3.12、uv锁、runtime-v1.5。统一安装保留全部已声明extras，避免无extras的同步移除已有RAG依赖；router关闭不等于卸载历史SDK。缓存安装与首次联网安装的证据要区分。NFS启动使用no-recreate复用既有容器/IP和named volumes，升级不是隐式启动操作。

## 2. 固定数据与缓存

| 场景 | 文件数 | 单文件字节 | 初始总字节 | 后续修改 |
|---|---:|---:|---:|---|
| few-files | 4 | 1,024 | 4,096 | 无 |
| many-small-files | 32 | 256 | 8,192 | 无 |
| partial-change | 8 | 4,096 | 32,768 | 修改1/8文件，保持文件长度，带旧hash CAS |

固定种子20261018，ASCII合成文本与换行、稳定相对路径；报告保存数据hash。每场景3个独立工作区，单并发；每Pod两次list_files预热，不清理内核缓存。读取紧跟写入，属于暖缓存读，不是冷启动磁盘吞吐。工具观测、Docker/Kubernetes查询也有开销，不把每项毫秒都解释为纯NFS延迟。

第一轮固定负载与Python回归并行，保留为探索记录；正式延迟基线另在本Agent不并发执行测试/安装时测量。Docker/Kubernetes与宿主其他后台负载未完全隔离，不宣称无噪声实验。

## 3. 指标解释

- 文件工具端到端时间：Python HTTP → Go归属/策略 → exec → gVisor helper → NFS → 响应并核对hash。创建、CAS更新、读取分开；包含固定执行边界开销。
- prepare：PV/PVC和可信目录初始化/检查等；claimReady：业务Pod创建、就绪、NFS挂载及真实读写检查的组合时间。不是单独mount系统调用延迟。
- P50为中位数，P95为观测值排序后的线性插值。Pod每场景仅3次、CAS仅3次，尾部样本很少，不能据此承诺95%生产请求。
- 资源：CPU累计计数差、RSS/内存端点样本，明确对应Go/控制器/NFS；端点样本不是峰值。集群节点与其他服务开销不能从Go进程CPU推断。
- 网络：NFS容器eth0累计收发字节差，包含数据、mount、元数据与协议；是容器级窗口，不是精确单文件负载计数。不是公网账单，也不含全部HTTP/exec路径字节。去重上传量与这些计数不同。
- 输入seed、随机数据、轮数、镜像、硬件、部署位置、缓存和并发均记录。读写hash、完整清单、Pod实际gVisor/NFS、停止证明必须通过才将本轮算成功。

## 4. 恢复测量的边界

入口实验记录：首次agentd启动至API可用、强杀至API可用、强杀至新Pod观察到、强杀至read_file完成被观察到、强杀至Task完成。使用控制器单调时钟；轮询有观察误差。文件读回后，Replay还故意等待8秒，最终完成时间含这段等待。

源码在WSL的Windows挂载盘，Python依赖加载约数十秒；这部分进入当前启动/恢复样本，不能当NFS挂载本身的耗时。旧Task预算与阶段时钟必须保持，停机时间照计，不为了测得更好结果重发120秒预算。检查写操作仅一次，并按原始调用账本统计额外读取；没有调用模型作质量或恢复评分。

本机墙钟已存在回拨观察，生产保护保持。跨进程业务证据保留原时间戳，耗时以单调时钟观测；不因失败回拨而更改系统时间或丢弃失败报告。

## 6. V2当前流量风险（代码分析，不是实测成绩）

Agent完整工具组及最终诊断均同步保存。当前Go在restic前后分别生成完整manifest，每遍读取全部用户文件并计算hash；仅此两遍逻辑读取约为`2 × 工作区有效字节 × 检查点数`，另有restic扫描/读取。页缓存可能减少实际NFS传输，不能用逻辑读取估算冒充容器网络计数。当前工作区限制64MiB/512项、单文件256KiB，大于此范围的工作区不是当前可运行能力。

restic分块去重减少仓库新增数据及上传，不能消除manifest扫描；当前使用`--no-cache`，维护Pod也不共享持久缓存，仓库元数据请求应单独测量。本机NFS与专属MinIO都在Docker/kind私网，备份不等于公网上传；未来跨主机、跨可用区或外部对象存储部署需重新核算。当前Replay外部模型调用为0，首次镜像/依赖下载另计。

此段为实测前的代码分析。后续第7～8节分别记录manifest逻辑读取估计、NFS/MinIO窗口收发、restic逻辑/压缩新增、备份/恢复时间与仓库统计；逐对象请求数未采集，不能推算对象请求费用。端点相加可能对同一传输重复计数，不报告为公网账单；不从去重直接推导运行I/O提速。

## 7. V2同条件后端微基准方法

入口复用第2节seed/文件数/长度/局部CAS修改，先使用同一`.cache/workspace-sandboxd-owned-cleanup`重跑V1，再串行测V2；不拿旧版本Go二进制的历史基线直接作本轮差值。

上述为既有原始实验使用的二进制。交付入口已去掉该历史缓存依赖：先`bash hack/workspace.sh build-storage`，再`bash hack/workspace.sh benchmark-v2 --repeats 3 --output .cache/<新报告>.json`，默认使用其`.cache/workspace-sandboxd`和校验过的原生restic安装路径；需要固定历史二进制时显式加`--binary .cache/workspace-sandboxd-owned-cleanup`。每轮仍先用所选同一二进制测V1再测V2，报告保留实际SHA。此路径修复不重算下文原始成绩，也不声称在另一二进制上重新测得相同数值。

```bash
agentd/.venv/bin/python -m agentd.workspace_checkpoint_benchmark \
  --repeats 3 --output docs/evidence/<新的报告名>.json
/usr/bin/python3 agentd/workspace_checkpoint_benchmark_audit.py \
  --source docs/evidence/<报告名>.json --output docs/evidence/<新的审计名>.json
```

每个V2试验使用新独立仓库、controller、Secret、工作区和Go控制目录，owner marker在基线统计中单列。一次首次备份、一次后续备份（局部修改场景改1/8文件，其余不改文件），然后恢复首次版本到新空目录并核对所有文件hash；不共享仓库去重缓存掩盖“首次”成本，不删除任何既有快照/卷。2次list预热、暖读、不清内核缓存，与V1相同。本任务不并发测试/安装，宿主与Kubernetes其他后台未完全隔离。

进程生命周期并非完全相同：V1沿用原基线的单Go进程/9个新工作区，V2因每仓库绑定配置而每试验新开Go。工具计时都在两次RPC预热之后；prepare/claim的连接历史仍不同，只作描述，不能把其差值全部归因备份。本文“同条件”指固定数据、二进制、文件工具预热、并发和部署位置，不宣称随机化或全系统缓存完全相同。

这是**可信后端维护微基准**：一批文件写完后做一次备份；真实Agent默认每完整工具组及最终诊断保存，不能把这里的两次批量备份冒称为默认Agent整任务时延。后端receipt显式标记sessionBound=false，不伪造Session COMMITTED；正常联合提交/恢复另由文档47、48真实证据证明。

- `rpcMs`为reserve/start/wait/finish四次真实HTTP耗时之和，含真实Pod启动/扫描/上传；`observedPauseMs`还包含CRI与日志取证及receipt fsync，`observationMs`另列。
- `batchRpcMs`为本批计时文件RPC与两次备份RPC之和。`batchWithCheckpointsMs`还包含资源采样、仓库统计等观测成本，不把它们全部当成生产备份开销。
- 恢复同时报告四个restore RPC之和，以及新目录prepare、restore、runtime观测、claim/list全量hash核查、release的总时间；二者不同。
- NFS、MinIO、kind节点分别采集eth0收发及cgroup CPU/内存端点。Go/控制器有进程CPU/RSS端点；不包含控制器子进程CPU，kind包含维护Pod及全部K8s后台，均不是峰值或严格单组件归因。计数器回退时拒绝统计，不截成0。
- restic `data_added_packed`是新增压缩pack数据，另记录逻辑新增和处理字节；MinIO RX/TX是实际容器窗口流量，含HTTP/元数据/协议，不能等同纯PUT或公网账单。两个端点相加可能重复计数同一传输。
- 网络/资源窗口分别围绕备份和恢复；owner初始化与窗口外Native仓库统计的网络没有并入，因此不是整轮V2所有网络总量，也不直接与V1整个试验的累计字节作差。
- 仓库记录`stats --mode raw-data`原始字段，以及MinIO专属前缀`du -sb`表观字节（含目录/元数据，不是S3计费或磁盘块分配量）。owner基线、首次后、后续后分别保存；小文本固定开销可能占主导，不预设去重后一定更省。
- 未采集逐对象API请求数和峰值内存；这些不由容器字节数反推。第一次/后续/恢复每场景只有3份样本，P95仍是插值描述，不能作为生产SLA或GB级工作区估计。

## 8. V2实测结果

原始[V2 JSON](evidence/phase9-v2-fixed-workload.json)、[本轮V1 JSON](evidence/phase9-v2-fixed-workload-v1.json)、[命令输出](evidence/phase9-v2-fixed-workload-command.txt)、[独立审计](evidence/phase9-v2-fixed-workload-audit.json)。V1/V2各9/9通过，9个独立新仓库、18次备份、9次首次版本恢复；外部模型0。工作区、版本、Secret和控制日志均保留，没有forget/prune。

|---|---:|---:|---:|---:|---:|
| few-files，4 KiB | 1600.60 | 14691.46 | 6663.67 / 7693 | 7091.82 / 7794 | 14626.50 / 15053 |
| many-small-files，8 KiB | 12802.18 | 26608.85 | 8039.65 / 8047 | 7879.31 / 7886 | 14590.51 / 21436 |
| partial-change，32 KiB | 3401.77 | 17545.38 | 7821.65 / 8064 | 7680.01 / 7871 | 15444.08 / 19673 |

首两场景后续源文件完全不变；第三场景改1/8文件（同长度、仅替换第一文件前8字符）。每格备份/恢复只有3个样本，不把插值P95描述成稳定尾延迟。RPC之和不含取证/仓库统计；仪器化batch总时间与pause均在原JSON另列，不与V1的原始I/O窗口混为“纯后端差值”。

写RPC仍约200ms：few场景V1/V2 P50分别200.31/201.09ms，many为199.69/200.27ms，partial为200.78/200.52ms。读RPC的V1约199～200ms，V2三个场景P50为42.68/197.90/40.16ms。这些读延迟发生在备份完整扫描之后，连接/缓存与时序历史不同，未做分层profiling，不支持把变化直接归因于restic或NFS本身提速。

### 8.2 数据去重与实际容器流量（每格为3次的中位数）

| 场景 | 首次新增packed字节 | 后续新增packed字节 | 首次NFS双向字节 | 后续NFS双向字节 | 后续MinIO接收/发送字节 |
|---|---:|---:|---:|---:|---:|
| few-files | 5464 | 0 | 38110 | 27510 | 62007 / 70252 |
| many-small-files | 13566 | 0 | 156926 | 103162 | 62014 / 74091 |
| partial-change | 34701 | 5446 | 83680 | 41944 | 71591 / 72655 |

**不变不等于零流量。** 4 KiB工作区第二次新增packed数据为0，但MinIO窗口仍收到约60.6 KiB、发出68.6 KiB，NFS窗口双向约26.9 KiB。仓库元数据、标记验证、锁/快照与协议仍有开销；采样覆盖整个端点，不把每个字节强行归因于某一HTTP请求。未采集请求数，不能由这些字节推出PUT/GET账单。

每次manifest前后读用户文件的逻辑估计分别合计8/16/64 KiB，另有restic读取；这不是实测NFS字节下限，因为页缓存可能减少网络读取、metadata也会增加网络量。少量小文件的metadata比例明显，但当前只是小样本，不外推GB级工作区和数百并发。

| many-small-files | 58035 | 100091 | 105155 |
| partial-change | 58034 | 120314 | 153097 |

每仓库包含owner+2个业务快照。few场景packed不增加但新snapshot元数据使前缀继续增长；partial保留两版数据共享，原始`raw-data`统计另存，不拿它与V1“只留最新一份”比较后声称节省。小数据下固定元数据可大于文件正文，不能把`du -sb`当云对象计费量。

备份窗口资源中位数：Go CPU约0.05～0.07秒，NFS0.070～0.088秒，MinIO0.122～0.136秒，整个kind节点4.172～4.599秒。节点包含维护执行器与所有K8s后台，控制器的子进程CPU也未计入控制器自身值，不能把四者简单相加当纯备份CPU。

备份采样内存端点范围：Go RSS35.05～36.36MiB，NFS cgroup13.50～17.69MiB，MinIO79.48～117.95MiB，整个kind节点2873.52～2931.05MiB。它们是采样端点与不同统计口径，**不是峰值**；CPU/网络/内存逐窗原值均在报告。

### 8.4 有效性与未完成项

独立标准库审计重算seed数据、两组数据hash、每次manifest、Go控制日志checksum/阶段、资源计数差、分位数和恢复来源，确认9个仓库crypto均独立、18个snapshot均不同；它不是第二次性能运行。相关7项纯逻辑测试检查固定数据、统计、计数回退和不覆盖旧证据；性能时段未并发执行这些测试。

结论：当前实现能用去重减少后续新增pack数据，仍付出同步维护与扫描成本。这里测到的是受限Go后端、gVisor、NFS和MinIO的组合，保留第7节的进程/缓存/小样本限制。统一V2入口及十项证据审计随后已验证，最终交付状态见[49](49-工作区V1V2逐项验收与交付审计.md)，不能仅凭微基准通过宣布整个目标完成。
