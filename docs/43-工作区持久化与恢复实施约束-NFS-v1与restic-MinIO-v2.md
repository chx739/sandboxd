## 3. 身份与数据归属

### 3.1 身份定义

| 字段 | 生命周期与用途 |
|---|---|
| session_id | 整棵事故会话树，跨多次运行保留 |
| branch_id | 一条会话演进路线的稳定身份；分支头变化时 ID 不变 |
| node_id | 一条消息节点；只有标记为完整交互边界的节点可作为恢复点 |
| task_id | 一次逻辑 Agent 运行；故障自动接续仍属于原 Task |
| attempt_id | Task 的一次执行尝试；agentd 重启或执行环境接管时记录新尝试 |
| sandbox_id / pod_uid | 当前执行资源；替换 Pod 后发生变化 |
| workspace_id | 持久工作区身份，独立于 Task、attempt 和 Pod |
| checkpoint_id | V2 中已保存会话边界与文件版本的联合记录身份 |

自动接续与手动 resume 必须分开：自动接续保留 task_id；用户手动 resume 创建新 task_id，记录来源并继续受当前配置的任务预算约束。自动接续不得伪装为手动 resume 来重置限额。

当前 Session 通过父链和活动叶子表达分支，branch_id 是本阶段新增的稳定登记。旧 JSONL 必须兼容；旧无 branch_id/attempt_id 的记录可以作为 legacy 分支/尝试读取，不能批量改写历史。

### 3.2 逻辑关系

~~~text
session-001 / branch-main
  ├── workspace-001
  └── task-A
        ├── attempt-1 → Pod-A
        └── attempt-2 → Pod-B，自动接续同一工作区

用户后来手动继续：
session-001 / branch-main → task-B → 新 attempt / Pod
                         → 仍可绑定 workspace-001，前提是没有活动写入者

V2 从历史节点另开路线：
session-001 / branch-experiment → workspace-002
                               → 从该节点对应快照恢复，不覆盖 workspace-001
~~~

一个工作区同一时刻只允许一个活动写入者。即使当前只有单 Worker，也要拒绝重复恢复、并发认领和旧 attempt 写入。

### 3.3 存储分工

| 数据 | 权威存储与访问方式 |
|---|---|
| 报告、脚本草案、配置草案 | NFS 专属工作区，挂载到当前 Pod 的 /workspace |
| Session JSONL、分支工作记忆、长期记忆 | 沙箱外的持久控制目录；恢复不能依赖故障 Pod 的磁盘 |
| Task/attempt、工作区归属、预算、取消、分支头、检查点 | 各自单写入者负责的持久元数据日志 |
| V2 文件快照 | restic 仓库，后端为 MinIO 的项目专用 bucket/prefix |
| Token、restic 仓库密码、存储凭据 | 仓库外配置或受控 Secret，不写入工作区、JSONL、模型输入或 PR |

控制目录不使用 /tmp 或工作 Pod 的 emptyDir。agentd 重启实验要求该目录仍存在；整个控制盘丢失的灾备不在本轮承诺内。

## 4. 公共实现约束

### 4.1 统一业务文件路径

目标调用路径：

~~~mermaid
flowchart LR
    A["agentd 文件工具"] -->|"结构化请求"| B["Go sandboxd：归属、路径和参数校验"]
    B --> C["gVisor Pod 内受限文件操作"]
    C --> D["/workspace：专属 NFS 目录"]
~~~

- 保留 list_files、read_file、search_files、write_file、edit_file 的语义与有界输出。
- Go 侧重新校验工作区绑定、当前 attempt/代次、相对路径、symlink、文件类型、大小及 CAS；Python Policy 不是最后边界。
- 不新增任意 Shell、任意 argv 文件访问、宿主绝对路径、自由 NFS 路径或任意存储 endpoint 参数。
- 需要 Pod 内文件 helper 时，使用固定操作和有界结构化输入；禁止拼接 Shell。
- 保留现有单文件 256 KiB、路径深度/长度、搜索/列表、SHA256 条件写和原子替换约束；NFS 目录不能继承 emptyDir 的 sizeLimit 语义，工作区总量限制要另做有界校验并说明能力边界。
- 完成迁移后，agentd 按 task_id 保存业务文件的目录退出默认运行路径；本地 FileWorkspace 可保留为离线夹具和单测后端。
- 不立即删除旧目录。提供显式、限定于本项目旧工作区的迁移流程、文件 hash 核对和归属映射；缺少映射时明确说明文件未恢复。

### 4.2 Pod 创建与预热池

工作区卷在 Pod 创建时确定；不通过修改已创建的通用预热 Pod 来更换工作区。

V1 优先采用带 workspace_id 的按需创建路径；保留原无状态预热池及 CAS 行为。实际性能报告必须标明该路径，不能套用旧预热命中数据。

Pod 只挂载当前工作区。NFS 根目录、其他工作区、控制目录和备份仓库均不暴露给不可信沙箱。沿用 runsc、非 root、只读根文件系统、drop ALL、RBAC 和现有网络边界。

### 4.3 控制元数据

MVP 使用标准库文件能力和 JSONL，不新增数据库。不同服务的日志各有唯一写入者；不能让 agentd 与 sandboxd 无协调地同时追加同一日志。

- Task/Session/分支与预算由 agentd 的单写入控制路径维护；工作区授权及 Pod 绑定由 Go 侧验证并持久化。
- 日志追加须 flush/fsync，处理截断尾记录；关键索引可重建，不以只存在内存中的字典作为恢复依据。
- 原子替换与新文件创建要落实到本地 Linux 文件系统的持久化语义。损坏的完整记录应报错，不能跳过后继续写出“恢复成功”。
- 启动时阻止同一控制目录的两个活动 agentd 实例。本轮不实现分布式 Worker 或 leader election。
- Pod 标签可辅助查找，但不能作为唯一授权或持久化真相；校验 workspace、attempt、Pod UID 和当前绑定。

具体模块拆分可以随代码调整；上述责任和不变量不能因“简化实现”而省略。

## 5. V1：NFS 最新状态与自动接续

### 5.1 必须完成

1. 为新会话主分支生成稳定 workspace_id，创建 NFS 专属目录并挂到沙箱。
2. 文件工具实际通过新路径操作该目录，不保留默认双写副本。
3. 运行结束、取消、释放 Pod 时保留业务工作区；删除 Pod 不等于删除工作区。
4. Pod 故障后自动替换执行环境，保留 task_id、session_id、branch_id、workspace_id，新增 attempt 并重绑 sandbox_id。
5. agentd 启动时自动读取持久任务记录，接续符合条件的 queued/运行中/中断任务；不要求用户手动调用 resume。
6. 对外可查询 Task 当前 attempt、工作区、资源绑定、恢复状态及失败原因，沿用 Agent Token 保护。

### 5.2 自动恢复资格与预算

自动恢复只处理未完成且未取消、未超时、未超预算的 Task。

- 持久化模型轮数、工具次数、Provider 选择、已用/预留调用额度、原始截止时间和恢复尝试次数。
- 截止时间包含服务停机时间；重启不能把原来的 120 秒循环预算重新发放。claim、循环、清理的既有独立预算语义也须保留。
- 外部调用发起前先持久化额度预留；崩溃后无法确认用量的调用按保守占用处理，不能当作零成本重发。
- 自动接续不重新运行每 Task 一次的 Jev 选模；恢复已确定的模型配置。Replay 的执行游标也不能简单重置为第一条。
- 每 Task 自动恢复次数有界、持久化且可配置；初版默认最多 2 次自动恢复，超限进入可解释的失败状态。
- succeeded、cancelled、limit_exceeded、明确终止的 failed 不自动复活。
- 用户取消请求须先持久化再中断执行，取消与接管竞态中取消优先。
- 服务退出/进程崩溃与用户取消分开记录；不能因 Worker 关闭就把所有未完成任务记成用户取消。
- 已向调用者确认接收的 steer/follow-up 须保存命令 ID 和应用游标，恢复时不丢失、不重复注入；不要求恢复未确认接收的请求。

本轮真实外部模型测试仍需独立授权。自动恢复机制不增加任何历史模型预算。

### 5.3 同一 Task 的多 attempt

现有 Session 的 run.started、transcript 等查询主要按 task_id 组织。新增同 Task 多 attempt 后，要按 task_id + attempt_id 定位本次前缀与父节点，保留 legacy 读取，防止重复 transcript、前缀不一致和错误分支串入。

启动恢复先处理旧 attempt 的资源归属，再创建新 attempt。不得只重新调用 enqueue/resume 生成新 Task 来绕过这项改造。

恢复模型上下文仍从最后完整交互边界构建，保留工具调用/结果配对、工作记忆、来源与 60 秒状态时效规则。

Trace 按 attempt 保留，并可从 Task 汇总查询。不能用最终一次运行的 JSON 覆盖较早 attempt 的故障、调用用量和工具证据。

### 5.4 单写入者与结果不明

1. 发现异常后暂停该 Task 的新工具调度。
2. 核对旧 Pod/attempt，确认旧执行者已终止或已真正丧失写能力。
3. 更新持久绑定代次，再创建和绑定新 Pod。
4. 验证专属 NFS 工作区可读写后恢复调度。

NFS/RWX 不保证单写入；仅增加 generation 数值、租约过期或从 API 删除 Pod 对象，都不能自动证明网络分区中的旧进程已停止。本轮在单节点可控故障中验收；无法确认旧实例停止时，应阻止接管并报告原因。

已完成的历史工具不重放。执行中断时：

- 只读工具可按显式、有界策略重新查询，但要记录新观测和预算。
- 写文件若结果不明，先核查目标 hash；不直接再次覆盖或编辑。
- Plan、审批及外部变更不得通过恢复逻辑自动重新提交或执行。
- 不完整工具组不进入可恢复上下文；保留中断审计，明确说明文件可能领先于最后会话节点。

### 5.5 V1 会话与文件恢复边界

V1 只有最新持久文件，不保存某个 node 当时的文件树。

- 允许读取旧会话树、节点、消息及证据。
- 最新活动路线的自动接续/手动继续可绑定当前工作区，但要检查活动写入者并重新核查当前文件。
- 请求从旧节点恢复或另开携带工作区的分支时，返回明确的“当前后端无对应历史文件版本”错误；不能偷偷挂载最新文件。
- 保留原 Session 的纯读取与离线测试兼容，不删除历史节点来规避限制。
- NFS 上的可写目录不得作为不可变 checkpoint 来登记，不承诺文件与会话节点精确一致。

## 6. V2：在 NFS 上增加 restic + MinIO 历史快照

### 6.1 固定架构与触发方式

~~~text
NFS 业务工作区（运行时权威）
       ↓ 完整交互边界，暂停工作区写入
受信任的备份执行器 / restic
       ↓
MinIO 专用 restic 仓库
       ↓
检查点元数据绑定完整 Session 边界
~~~

- 初版使用同步检查点；先跑通一致性再考虑异步上传。当前 V2 不包含后台异步流水线。
- 每个完整工具轮次结束、以及最终诊断持久化后，保存联合检查点；不得在半组工具消息中提交。
- 整个扫描和上传阶段保持工作区写入屏障，限制耗时；不暂停外部写入却宣称获得同一时刻的文件状态。
- 可信备份执行器可采用受限维护 Pod/进程，固定输入范围，凭据不进入不可信业务 Pod；不为此新增通用 Agent 工具。
- restic 接管分块、去重、压缩、加密和文件树；不自行重写这些机制，也不手动修改仓库对象。
- 保留 NFS 运行意味着本配置仍依赖可用 NFS。MinIO 保存备份不等于 NFS 服务故障时可以立即无存储运行。

### 6.2 检查点记录

下例是字段示意，尖括号内容由程序填充；它不是当前已存在的数据。

~~~json
{
  "schema_version": 1,
  "checkpoint_id": "cp-<uuid4hex>",
  "parent_checkpoint_id": "cp-<parent-uuid4hex>",
  "session_id": "session-001",
  "branch_id": "branch-<uuid4hex>",
  "session_node_id": "node-0018",
  "session_ref": "<已持久化会话前缀的定位和校验信息>",
  "workspace_id": "workspace-<uuid4hex>",
  "task_id": "task-001",
  "attempt_id": "attempt-<uuid4hex>",
  "revision": 18,
  "storage": {
    "backend": "restic",
    "repository_id": "repo-001",
    "snapshot_id": "<restic返回的完整快照ID>"
  },
  "image_ref": "<固定镜像引用>",
  "image_id": "<实际不可变镜像身份>",
  "file_manifest_sha256": "<有界文件清单校验值>",
  "status": "COMMITTED",
  "created_at": "<UTC时间>",
  "committed_at": "<UTC时间>"
}
~~~

- checkpoint_id 在首次请求时用 UUIDv4 生成并持久化，重试复用；不引入雪花算法，不为 UUIDv7 升级当前 Python 3.12。
- revision 是分支内成功提交序号，由单写入者在提交时分配；唯一约束是 branch_id + revision。
- parent_checkpoint_id 表达历史关系；branch head 指向最新已提交检查点，不能用最大 ID 或创建时间代替。
- snapshot_id 由 restic 返回，必须连同 repository_id 保存；它与 checkpoint_id 不互相替代。
- session_ref 至少能定位并验证所选父链；只留 node_id 却没有可读取的节点内容不算可恢复。
- 记录实际镜像身份，避免仅保存可变 tag；本地镜像 ID 与 registry manifest digest 要注明类型，不混称。
- 同一个文件快照允许被多份联合检查点引用，前提是程序证明文件未变化并正确维护引用；初版优先每次正常创建快照，避免跳过后缺少 snapshot_id。

### 6.3 提交协议

~~~text
PREPARING → DATA_READY → COMMITTED
    └───────────────→ FAILED
~~~

1. 获取该工作区写入屏障，固定本次完整 Session 边界。
2. 持久化 Session 节点和 PREPARING 记录，保留同一个 checkpoint_id 作为幂等键。
3. 执行 restic 备份，检查退出码及结构化结果，核对文件清单与完整 snapshot_id。
4. 持久化 DATA_READY，然后校验分支头和当前 owner/attempt 未改变、任务未被取消。
5. 用一条可恢复的 COMMITTED 日志记录同时表达检查点成立与分支恢复头前移，再 fsync；缓存索引可以重建。
6. 释放写入屏障，允许继续运行。失败保留上一份已提交检查点，明确报告失败或降级，不伪报保存成功。

restic 部分文件无法读取时的非零退出码不能当成功。备份成功、元数据未提交时产生的孤立快照先保留、核查，不能立即清空仓库。

会话最新完整节点与文件最新已提交检查点是两种进度。自动恢复必须明确所用模式：

- NFS 最新目录仍可用：沿用 V1 最新状态接管与核查逻辑，不默默用旧备份覆盖它。
- 显式从检查点恢复：会话与文件都选该检查点，写入新的空工作区；原 JSONL、原分支、原目录保留。
- NFS 工作区丢失：仅在已有可用 NFS 恢复目标时恢复已提交快照，并明确回退点；无法提供目标时停止，不能虚称跨存储故障接管。
- 无论回退到哪个节点，Task 已消耗的预算、原截止时间和操作审计都不回退。

### 6.4 历史分支、删除与保留

- 从有对应 COMMITTED 检查点的完整节点分支：新建 branch_id 和 workspace_id，从快照还原到新空目录，再运行；不覆盖原分支。
- 无对应快照、快照损坏或被遗忘时返回明确原因，不静默使用邻近版本或最新文件。
- 工作区文件删除后，新快照应体现文件已不存在，旧快照可保留；恢复到空目录后核验没有旧文件残留。
- 初版默认不自动 forget/prune，提供受控管理命令、预览和引用检查；不把清理接口暴露为 LLM 工具。
- 每条保留分支的恢复头、被明确保留的检查点和正在使用的恢复源都要受保护。
- 忘记检查点时先更新可恢复状态与引用，再由 restic 自己执行 forget/prune；不直接删除哈希块或 MinIO 对象。
- 清理与备份串行安排，仓库锁冲突有界失败，不取消锁后强行并发执行。

## 7. 环境、兼容与迁移

实施前检查并记录：

1. 当前 WSL、Docker、kind、runsc、Kubernetes、Go/Python、现有服务、端口、内存和磁盘；本轮文档编写未完成环境验收。
2. NFS 服务端与节点挂载能力、非 root UID/GID、导出与目录权限、gVisor 实际读写；不能通过放开特权业务 Pod 绕过失败。
3. restic 固定版本、二进制校验和、容器镜像摘要、MinIO S3 兼容和 TLS/凭据配置；不使用浮动 latest。
4. 已有 Milvus MinIO 是检索服务的依赖，不将其 bucket 当工作区仓库。若复用服务，创建专用 bucket/prefix 和权限；不得更改或删除旧检索对象及卷。
5. Session、Task 与工作区的迁移映射和回滚步骤；旧无映射会话明确标注“仅上下文可恢复”，不能声称文件已恢复。

迁移采用新增元数据与适配读取。功能开关可保留旧离线路径，但真实 V1/V2 验收必须走 Pod 文件工具、NFS 以及实际 restic/MinIO，不得以 Fake 或本地目录冒充。

## 10. 性能评测与能力口径

固定小规模合成文本工作区，覆盖少量小文件、多小文件、局部修改；不为测评引入任意脚本执行或突破文件工具上限。固定数据、种子、修改比例、重复次数、缓存状态、硬件与 NFS/MinIO 部署位置。

报告至少包括：

- 文件工具读写 P50/P95、Pod 创建/挂载耗时、故障发现至工具再次可用的分段恢复耗时。
- agentd 启动至符合条件 Task 接续的耗时，失败率、恢复次数、重复检查次数和是否发生重复写入。
- V2 首次/后续快照时间、实际上传量、去重与压缩统计、仓库占用、CPU/内存和恢复到空目录的耗时。
- NFS V1 与 NFS + restic V2 的同条件对比；明确同步备份的额外等待。
- 数据丢失范围按已确认持久文件、完整 Session 边界、COMMITTED 检查点分别描述，不能统一声称“零丢失”。

当前 V2 仍在 NFS 上运行，不能直接宣称日常 I/O 更快。历史版本占用也不能直接与“V1 只存最新一份”比较后声称更省；去重收益应与同样保留版本数的全量备份基线比较。

本地盘运行 + restic/MinIO 是后续实验候选，**不属于本次默认 V2 验收**。没有实现和实测不得写“性能提升”。单节点小样本不外推为生产 SLA。

## 11. 非目标与变更规则

本轮不实现：NFS/MinIO 高可用、节点/可用区灾备、网络分区下无条件接管、多租户、分布式调度器、数据库、Git 工作区版本管理、Kopia、进程内存/容器运行现场恢复、任意 Shell/脚本执行、自动审批或新一轮付费模型测评。

技术实现中的局部文件名、结构体和部署模板可按现有代码调整，并记录理由。下列改变必须先询问用户：

- 把 V1 扩成历史文件版本，或让 V1 旧节点静默使用最新文件。
- 把 V2 默认改成本地盘，或换掉 restic/MinIO。
- 放弃 agentd 重启自动接续，改变 task/attempt 语义，重置预算或截止时间。
- 删除业务文件或旧索引/卷、扩大系统权限、引入新基础设施、扩大真实故障范围或外部费用。
- 发现已确认路线在当前 gVisor/WSL 环境不可行，需要更换关键技术。

不得因为任务复杂就自行缩减为“挂载成功”的演示；也不得因为讨论过生产方案就增加生产级范围。
